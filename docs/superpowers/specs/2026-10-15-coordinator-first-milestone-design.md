## 目标与范围

用户已确认先完善协调 Agent，首个可观察结果为：提交需求 → 协调 Agent 自动调用产品 Agent → 得到需求文档和验收标准 → 等待用户明确确认。

本里程碑提供协调角色、最小产品角色、共享文件契约、配置读取规则与状态检查步骤。首个真实调用验证在 Codex 中进行。用户确认后可以记录审批并将阶段置为 development，但本里程碑在该阶段停止，提示开发调度尚未接入，不派发未实现角色，也不将整个需求标为完成。

宿主提供子 Agent 工具；框架自身不再启动后台调度进程。首版同一需求只允许一个协调会话，其他会话发现占用时报告阻塞。

| 文件或目录 | 职责 |
| --- | --- |
| agents/coordinator-agent.md | 协调角色入口，按本文步骤派发任务和检查结果。 |
| agents/product-agent.md | 最小产品角色，读取输入、提出关键问题、输出完整需求和验收标准。 |
| workflow/ | 状态与交接契约、Codex 调用说明、配置字段说明。 |

| 目标工作空间/workflow.yaml | 工作空间需求根目录和默认文档策略，不存放凭据。 |

协调 Agent 使用宿主文件工具读取配置和状态、检查字段与证据、记录任务和审批，并通过宿主原生子 Agent 能力派发产品任务。角色定义和规则文件是执行入口，不新增独立 CLI 或运行时依赖。上述检查是 Agent 的执行规范，不提供程序级强制约束；实际子 Agent 调用及人工审批均须有会话证据。

README 提供在宿主会话中启动和恢复协调 Agent 的自然语言示例及能力清单。根 AGENTS.md 用简短的条件指针引导协调和产品任务读取对应角色文件。

## 配置契约

先明确目标工作空间根目录，从该根目录加载 workflow.yaml，解析 workspace.features_dir 后再查找需求。配置读取顺序：内置默认值 → 目标工作空间 workflow.yaml → 当前修订版 documents.yaml。按字段覆盖；列表整体替换。修订版 documents.yaml 只允许覆盖 documents 字段，不能改变工作空间、需求根目录或审批渠道。未知字段、非法值和配置解析错误应报错，并保留已有状态。

项目配置示例（待实现）：

```yaml
schema_version: 1
workspace:
  features_dir: agent-features
documents:
  provider: local
  feishu:
    parent_node_url: null
    write_enabled: false
approval:
  channel: coordinator
```

workspace.features_dir 默认 agent-features，仅接受相对工作空间根目录的路径，并校验真实路径不越出工作空间。框架安装位置、Shell 当前目录和目标工作空间可以不同，调度工具调用时均传入已解析的绝对工作空间及需求路径。改变配置不自动迁移已有目录，迁移按总设计规则显式执行。

单需求配置位于 revisions/v<N>/documents.yaml；需求阶段尚未创建文件时继承项目配置。示例：

```yaml
documents:
  provider: feishu
  requirements:
    url: https://example.feishu.cn/wiki/example
    access: read
```

provider 仅接受 local、feishu；approval.channel 首版仅接受 coordinator。文档项可分别覆盖 provider，以支持飞书需求正文与本地生成报告共存。

local 文档路径默认以当前修订版目录为根；继承来源使用 source_revision 定位已存在的来源修订版。解析后必须位于对应修订目录内。来源与 review/ 等保留输出位置冲突时阻塞；生成稿位于 review/requirements.md，不覆盖用户只读原文。feishu 文档使用链接，parent_node_url 仅决定新文档位置，不替代已有正文链接。

access 默认为 read，仅允许 read、read_write。已有文档只有在 write_enabled=true 且该文档 access=read_write 时才允许更新；新文档创建还要求配置 parent_node_url。写入前检查远端内容是否偏离基线，冲突则阻塞。即使开启写入，也保留历史修订和审批快照。写入权限与实际认证权限必须同时满足。

每次派发记录有效配置摘要。文档来源、链接或写入策略改变时，先使当前待审批展示失效，重新读取和展示；如果需求内容和验收标准不变，可以在同一修订版重新请求确认。内容发生范围变化时执行总设计的新修订版规则。

## 文档来源与快照

每份文档记录 kind（requirements、reference、design 或 test_report）、provider、location、access。requirements 为本轮正文来源；reference 为参考资料，内容变更本身不会直接改变需求范围。

在每次产品派发、提交评审、审批记录前及中断恢复时，读取必需文档并核对摘要。快照保存在当前 run 的 sources/ 下，包含正文、来源、读取时间、内容摘要，以及可取得的远端版本信息。仅快照完整且来源明确才能进入下一步；图片、附件或引用节点承载关键规则但未能读取时，记录缺失项并阻塞。

产品处理 read 文档时，在本地产出建议稿和相对原文的差异，向用户明确展示将批准哪份建议稿。审批绑定实际建议稿和其来源基线，而非把只读远端原文当成已更新。read_write 文档写回成功后重新读取，确认内容与建议稿一致，再提交评审。

远端内容变化不沿用旧快照冒充最新内容。协调 Agent 判断语义影响：纯排版变更更新来源记录；范围或验收标准变化按新版本处理；不确定时询问用户。不能完整读取时标记 blocked 并说明所需权限或缺失内容。

首个本地闭环必须完成真实产品子 Agent 调用。飞书策略和来源契约在本里程碑定义并校验；实际飞书读写需使用宿主可用的飞书能力单独验证。能力缺失时阻塞该需求，不回退为本地来源。尚未验证飞书路径前，README 明确标为未验证，不声称已支持。

## 协调执行步骤及完成条件

1. 识别需求。按名称与目标项目匹配已有记录，核对内部 ID；新建、续改或独立需求的意图明确后再写入。匹配存在歧义时保存问题并等待用户。
2. 读取当前状态及配置。新建后先读取生成的 status.yaml，恢复已有需求则在任何修改前读取。核对活动任务、修订版本、目录和目标项目规则；完成条件是配置有效、身份唯一且没有未核实的活动任务。
3. 准备产品输入。将用户原始诉求、目标项目、基线、变更说明、已有答复和必读快照写入本轮输入。缺少目标项目路径或无法推断的关键业务规则时提出问题，保留 draft/waiting_user。
4. 派发产品 Agent。先写入 run_id、任务输入和 active_run，再用 Codex 子 Agent 工具启动产品角色；保存宿主返回的任务标识。完成条件是可追溯的派发记录，不能把写出任务文件视为已经实际调用。
5. 校验产品结果。校验内部 ID、修订版、run_id、结果状态与产物路径；读取每条验收标准检查其可验证性。needs_input 时汇总关键问题，保留 draft/waiting_user；ready 且文档和证据完整时进入 requirement_review/waiting_user。
6. 展示评审。向用户展示需求名称、版本、范围、差异、验收标准及实际文档位置，记录待审批内容摘要。明确请求对该版本的确认，等待用户答复。
7. 接收答复。只有答复明确对应当前待审批内容且再次核验内容未变，才记录原文、时间、会话、内部 ID、修订版和摘要。要求修改时依总设计规则处理；一般讨论或无明确对象的“可以”不自动视为批准另一个待审需求。
8. 停在里程碑边界。审批成功后阶段为 development，execution_status=blocked，原因 development_dispatch_not_implemented；审批保留有效，后续接入开发调度后方可解除。没有批准则继续等待，不能越过人工确认点。

## 产品任务与结果契约

产品任务包含 feature_id、requirements_revision、run_id、角色、绝对需求目录、目标项目、必读文件、原始诉求、已有答复、允许输出位置和完成条件。

产品结果使用结构化文件，状态仅为 ready、needs_input、blocked，包含相同身份字段、产物列表、问题、假设和阻塞原因。needs_input 必须提供具体问题；blocked 必须说明原因；ready 必须给出需求文档和验收标准。

需求文档包括目标、范围、非目标、约束、业务规则和相对基线的变化。验收标准可放在需求文档中，但必须有唯一编号、前置条件、操作与可观察结果。影响范围、业务规则或验收结论的未确认假设不能以 ready 提交。

产品角色只能写当前 run 的产物目录。协调 Agent 校验后将其固化为修订版评审稿，保留 run 原始结果；角色不得修改根 status.yaml、历史版本或目标项目代码。

## 失败与恢复

先持久化 run 意图，再调用宿主；宿主调用返回后立即记录任务标识。若在二者之间中断，active_run 的派发结果记为未知，恢复时查询宿主；查询不能证明旧任务结束时阻塞，不重复调用。

收到产品结果先持久化，后校验并推进状态。审批等待中断后重新展示同一内容并等待用户；不从历史摘要推断已经批准。收到已持久化的审批记录时核对其内容摘要，再按当前阶段恢复。

角色调用异常、无效结果和文档访问失败均保留业务阶段，记录 execution_status=blocked 和原因。问题澄清使用 waiting_user，待补充信息写入输入后启动新 run，保留原问题与结果。

## 验收场景

| 场景 | 预期证据 |
| --- | --- |
| 提交中文名称的新需求 | 生成唯一内部 ID 和合法初始状态，产品真实子 Agent 被调用。 |
| 原始信息不足 | 产生具体问题并等待用户，补充后可继续，未进入评审或开发。 |
| 产品产物完整 | 进入 requirement_review/waiting_user，展示实际产物和带编号验收标准。 |
| 用户未确认 | 不进入 development，不派发开发。 |
| 用户明确确认且内容一致 | 审批记录完整，进入 development 并明确报告开发调度尚未接入。 |
| 待评审内容变化 | 旧待审批摘要失效，按是否改变范围决定重新展示或新修订版。 |
| 同名需求续改 | 查到基线，按修复或范围变更处理，历史证据保留。 |
| 旧版本、旧 run 或缺失产物 | 拒绝推进状态。 |
| 配置覆盖与非法配置 | 字段覆盖可预测；非法配置不改变现有状态。 |
| 指定飞书但缺少读取能力 | 明确阻塞，没有伪造快照或改用本地文档。 |
| 等待用户时恢复 | 读取现有状态和产物，不重复启动产品任务。 |
| 派发结果未知时恢复 | 核实宿主任务或报告阻塞，不产生重复任务。 |

验证分为规则场景检查、真实 Codex 子 Agent 调用、飞书集成三类，分别报告通过、失败和未验证。首个真实调用使用独立演示需求，不能把演示需求的审批当成本框架实现需求的审批。
