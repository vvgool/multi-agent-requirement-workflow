# 宿主内多 Agent 需求协作设计

> 历史设计/实施记录：仅供追溯，不作为当前待执行计划。当前目标见 [整体规划](../../planning/overall-goals.md)，执行以 agents/、skills/、workflow/ 为准；验证边界见 [验证索引](../../verification/README.md)。

> 历史设计草案：以下状态及限制描述的是设计当时，当前实现与未验证门槛见 [README](../../../README.md)。

关联需求：宿主内多 Agent 需求协作闭环（内部标识 REQ-001）。状态：待用户审阅的设计草案，尚未进入实现。

## 目标与已确认约束

用户提交需求后，由协调 Agent 在宿主会话内自动调用产品、开发和测试 Agent。需求文档及验收标准必须经用户明确确认后，才能进入开发。开发与测试自动交接，测试失败返回开发。不自动执行生产发布。

需求目录以需求名称命名，内部保留自动生成、改名后不变的 feature_id。同名需求可能是在原需求上继续优化，必须先识别意图，并以修订版本保留历史需求、审批和验证证据，不能覆盖旧版本。

首版建议先验证 Codex，随后适配 Claude Code 和 OpenCode。本文中的三次开发尝试、串行执行和文件契约是建议默认值，尚未经用户单独确认。

首个里程碑已选定为协调 Agent 自动调用产品 Agent并等待人工需求确认，具体配置、文档来源及交接设计见 [协调 Agent 首个闭环设计](2026-10-15-coordinator-first-milestone-design.md)。后续开发、测试自动循环不计入首个里程碑完成范围。

## 方案选择

采用宿主内协调 Agent 加共享文件：宿主提供子 Agent 执行能力，文件保存业务状态。角色定义和状态契约跨宿主共享，调用方式由各宿主适配说明提供。

用户直接在 Codex、Claude Code 或 OpenCode 中启动协调 Agent。框架交付角色定义、宿主入口、流程规则、配置和文档模板；协调 Agent 使用宿主的文件读写及子 Agent 工具执行，不引入独立 CLI、Python 运行时或常驻调度服务。状态与证据检查由协调 Agent 按规则执行，不将提示词规则宣称为程序强制校验。

宿主会话关闭后不继续后台执行。恢复时重新启动协调 Agent，读取磁盘状态并核对已有任务，不能仅凭历史会话摘要推进阶段。

## 职责与状态归属

协调 Agent 负责读取状态、选择合法任务、调用角色、检查结果与证据、记录用户确认及推进状态。它不代替产品定义需求、不代替开发实现业务代码、不代替测试给出通过结论。

产品 Agent 负责澄清问题、需求文档和逐项验收标准。开发 Agent 负责技术方案、实现、开发验证和变更说明。测试 Agent 按已批准的验收标准独立检查，记录通过、失败及无法执行项；测试角色不修改业务实现。

各角色开始工作前通过派发中的需求目录读取 <features_dir>/<需求名称>/status.yaml，并核对内部 feature_id 和修订版本，只处理被派发阶段。角色写各自产物并返回结果，协调 Agent 统一更新状态和产物索引；角色完成时必须交回状态更新所需结果。一个需求同时最多有一个活动角色任务。首版不支持同一需求被多个协调会话并行驱动。

开发目标项目通过需求元数据中的绝对路径指定；开发和测试必须读取目标项目的 AGENTS.md。范围外改动、发布、推送和给他人发送消息不因自动调度而获得授权。

## 需求文件与角色交接

工作空间根目录由用户在启动协调 Agent 时指定，或明确采用当前工作目录；不得因框架文件所在位置而推断目标工作空间。读取该工作空间根目录的 workflow.yaml，workspace.features_dir 默认 agent-features，相对工作空间根目录解析，本文 <features_dir> 均指解析后的需求根目录。首版配置仅接受工作空间内的相对路径，拒绝绝对路径和解析后越界的路径。

框架的 agents/、workflow/、templates/ 留在框架安装目录；需求状态、修订版和执行记录放在目标工作空间下。历史 requests 目录仅在用户明确要求迁移后移动，保留内部标识值及相对产物路径；发现旧新两套目录时停止并报告冲突。状态字段统一为 feature_id，存量标识如 REQ-001 保持不变。

用户以名称创建和查找需求，不必提供或记忆 feature_id。内部自动生成唯一 feature_id，任何创建操作均不得覆盖已有目录。同名匹配先读既有需求，判断本次是修复、优化还是独立需求；仅有名称一致不足以自动判定为续改。多个匹配或意图不明确时向用户澄清。

名称支持中文和空格，拒绝空名称、路径分隔符、控制字符及 .、..，校验实际路径位于解析后的 features_dir 内，不能通过符号链接越界。名称比较采用 Unicode NFC 规范化并检测文件系统大小写冲突；规范化后重名也不得覆盖。不同目标项目中的同名需求通过目标项目元数据识别，独立建档时补充项目名等目录后缀。

<features_dir>/<需求名称>/ 下保存：

- status.yaml：不变的内部 ID、名称、当前修订版本及其阶段、执行状态、审批、活动任务、开发尝试次数和产物索引；是当前状态的唯一权威来源。
- revisions/v<N>/input.md：本轮诉求、目标项目路径、范围、约束、基线版本及相对基线的变更说明。
- revisions/v<N>/review/requirements.md：本轮生成的完整需求及带唯一编号的验收标准，与用户来源分离；历史产物仍按原索引使用。
- revisions/v<N>/design.md：开发产出的技术方案。
- revisions/v<N>/runs/<run_id>/：本轮每次派发、结果、开发证据和测试报告。
- revisions/v<N>/status.snapshot.yaml：切换到下一修订版前保存的本轮终态、审批和证据索引；历史快照不能参与当前状态推进。
- events.jsonl：跨修订版本追加记录阶段变化、派发、失败、审批、改名和恢复，每条事件携带内部 ID 和版本。

产物索引使用相对需求目录的路径。改名只能在没有活动任务时由协调入口执行，保留内部 ID、校验目标名称冲突并记录事件。外部派发不能仅凭旧目录路径定位需求，必须核对内部 ID；恢复时按内部 ID 重新解析目录，发现重复 ID 时阻塞。

## 同名需求与修订规则

| 场景 | 行为 |
| --- | --- |
| 当前版本开发或测试中，实现不满足已批准的验收标准 | 在当前版本内修复，增加执行记录，不改变批准范围。 |
| 新增功能、修改业务规则或改变验收标准 | 建立下一修订版，记录差异，进入 draft，由产品整理后重新提交人工需求评审。 |
| 已完成需求继续优化 | 基于已完成版本建立下一版，保留上一版 completed、审批及测试证据，不重新打开或覆盖上一版。 |
| 已完成版本出现缺陷 | 建立以缺陷修复为目标的下一版，引用旧版问题和回归标准，经确认后开发；不改写原完成记录。 |
| 同名但目标或用途独立 | 新建内部 ID，使用可区分的目录名称，按需记录关联需求。 |

首版每个需求只允许一个当前修订版，不支持版本分支并行开发。当前任务执行中收到范围变更，先停止后续派发、记录变更意图，等待现有任务结束或确认取消，再切换版本；无法确认旧任务结束时阻塞，不能与新版本同时写目标项目。

切换版本先持久化旧版状态快照，未完成旧版在快照中记录 superseded_by 和未完成原因，不能冒记为 completed。然后准备新版本文件，最后更新根 status.yaml 中的当前版本和初始 draft 状态并回读核对；审批、active_run 及开发尝试次数重新初始化。若中断留下未生效的新版本目录，恢复时以根状态为准核查，禁止再次创建并覆盖该目录。

新版本显式延续上一版有效文档策略、来源身份和权限；本地来源通过 source_revision 固定实际位置并重新读取。来源无法核实时记录 draft/blocked，不静默退回默认 local。生成稿位于 review/，写入前检查与来源不冲突。

v<N> 表示需求范围的修订版，状态写入次数另用 state_version；draft 内的文稿编辑不递增修订版。已提交评审后修改需求范围或验收标准，建立下一版；用户要求修改评审稿也遵循该规则。已批准的需求和验收标准不可原地改写，审批摘要校验失败时阻塞核查，经新版本重新评审后再恢复。

历史证据不自动视为新版通过；产品列明影响及回归范围，测试对新版验收标准给出证据。验收编号沿用语义不变的条目，新增条目使用新编号，删除条目在差异说明中记录。开发重试上限按修订版计算。

派发输入必须包含 feature_id、run_id、角色、需求版本、目标路径、任务范围、必读产物、输出位置及完成条件。任务结果包含相同标识、执行结论、产物路径、验证证据、未解决问题及阻塞原因。

协调 Agent 校验结果标识与活动任务一致、路径在允许目录内、产物确实存在且属于当前需求版本。迟到结果或旧版本结果不能推动状态。产物存在只是必要条件，还须检查其内容是否覆盖约定完成条件。

## 状态流转与人工确认

保留原有阶段：draft → requirement_review → development → testing → completed；测试失败回到 development。

execution_status 独立记录 idle、running、waiting_user、blocked，避免用业务阶段表达进程异常。

1. draft：协调 Agent 调用产品 Agent。存在关键问题时记录问题并等待用户；信息齐备且产品产物通过检查后进入 requirement_review。
2. requirement_review：展示需求、验收标准和版本，设为 waiting_user。仅用户针对该版本的明确确认可以写入审批并进入 development；超时、沉默或角色自评均不等于确认。
3. development：调用开发 Agent。只有改动说明、技术方案和开发验证证据齐备，才能进入 testing。开发任务报错仍留在本阶段并记录阻塞。
4. testing：调用测试 Agent。所有验收项有通过证据且没有未解决缺陷，才能进入 completed。失败报告列明验收编号、复现步骤、预期、实际和证据后，返回 development。
5. completed：记录最终产物和验证边界；本地测试通过不代表生产、真机或外部平台验收通过。

批准记录绑定内部 feature_id、修订版本、需求及验收标准内容摘要、用户原始确认文本、确认时间和来源会话。新版本不继承旧审批，需经 draft → requirement_review 重新确认；旧版本的审批保留为历史证据。检测到已批准文件被原地修改时，暂停调度并标记 blocked，不允许沿用审批。首次产品整理仍在 draft 内进行。

## 重试、中断与恢复

建议最多三次开发尝试，包含首次开发；测试失败消耗下一次开发尝试。达到上限后保留当前阶段、标记 blocked 并向用户报告剩余缺陷，不无限循环。

调用错误、超时和宿主中断区别于测试失败。任务失败不自动标记阶段完成，也不在不确定旧任务是否仍执行时重复派发。

派发前先记录 active_run 和 running，返回后先持久化结果，再校验并更新阶段。每次写入前重读并比较 state_version，写入后回读核对；使用宿主可用的文件工具记录递增版本。此方式不提供跨会话的事务或互斥保证，首版仅允许一个协调会话驱动同一需求，发现并发或不一致时阻塞。事件记录带状态版本；恢复时以 status.yaml 为当前状态，并核对已有结果、事件和活动任务，发现不一致先阻塞核查，不能猜测成功。

恢复时若宿主能查询活动任务，先查询或重新连接；若无法证明旧任务已结束，停止推进并说明原因。只有确认旧任务结束后才能重新派发。用户可明确解除阻塞或调整尝试上限，须留记录。

## 宿主适配边界

共享层定义角色、输入输出、状态和证据规则；宿主适配层定义如何启动、等待、查询和恢复子 Agent。不得把某个宿主专用工具名混入通用状态契约。

首版 Codex 必须通过实际子 Agent 调用验证产品 → 人工确认 → 开发 → 测试闭环。缺少子 Agent 能力时明确报告不支持并阻塞，不能悄悄改成由协调 Agent 扮演全部角色。

Claude Code、OpenCode 首版只保留扩展边界，不声明已支持。适配完成需各自在真实宿主内验证。

## 验收与实现边界

- 中文名称和包含空格的名称可创建、查找和恢复，内部 ID 自动生成且改名不变；重名、规范化冲突和非法路径均不覆盖文件。
- 同名续改能区分当前版本修复、范围变更、已完成后优化和独立需求；意图不明确时先澄清。
- 新版本保留上一版需求、状态、审批和测试证据，新审批前不能进入开发；开发尝试次数按版计算。
- 活动任务未确认结束时禁止版本切换或改名；旧版本任务结果不能推进新版本。
- 版本切换中断可识别未生效目录并恢复，历史版本不会被覆盖或误标完成。
- 未批准、审批版本过期或需求摘要变化时，无法进入开发。
- 错误角色、缺失证据、旧 run_id 和非法状态迁移被拒绝。
- 测试失败返回开发并携带缺陷，达到尝试上限后阻塞。
- 正常通过后保留完整产物索引，能追溯每条验收标准的测试证据。
- 中断恢复不丢失已持久化的产物，不重复执行未确认结束的任务。
- 使用临时目标项目在真实 Codex 宿主验证闭环；分别报告规则场景检查、宿主调用和目标项目测试结果。
- 不自动发布，不因一次宿主验证通过而宣称跨宿主支持。
