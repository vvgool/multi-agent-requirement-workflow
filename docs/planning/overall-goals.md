# 整体目标与改进方向

让用户在 Codex、Claude Code 或 OpenCode 中直接说明目标，由当前会话完成相关工作；需要时再启用专长角色、持久文档和独立验证。共享核心保持一致，各宿主使用自己的原生能力。

## 当前流程的取舍

| 需要解决的问题 | 当前做法 | 判断依据 |
| --- | --- | --- |
| 小修流程成本过高 | 当前会话定位、最小修改、相关回归并返回 | 一次性、明确、局部低风险且非旧任务续接 |
| 跨会话信息丢失 | task.md 汇总当前进度和阻塞，链接对应需求、设计及证据 | 确有恢复、交接或多步跟踪需求 |
| 角色交接膨胀 | 按专长委派，原生任务记录派发和结束 | 角色并非固定阶段链 |
| 人读文档费劲 | 先摘要和结论，再展开规则、设计或证据 | 文档应能独立理解，短表只放可比较的信息 |
| 风险与未知结果 | 具体范围确认、按需独立验证、未知调用查询原结果 | 项目规则和真实权限优先 |
| 多宿主和版本漂移 | 固定提交与包摘要，各宿主分别验证 | 文件安装、原生激活与业务闭环是不同证据 |

具体角色与流程见 [职责与工作流](agent-responsibilities-and-workflows.md)，执行边界以 agents/、skills/、workflow/ 为准。协议1/2历史任务继续使用原锁定包，当前文档不迁移历史记录。

## 本轮已落地的优化

- 为任务、规则、实现、设计、验证和缺陷补充稿提供明确的阅读结构与填写提示。
- 任务文档先显示当前结论，再呈现目标、验收、任务和真实验证；按需删去无意义的字段。
- 复杂需求在实施前拆分需求和技术设计，按依赖安排实施单元，验收时维护证据；进度集中在 task.md，正文各自维护，不等入口过长才拆分。
- 规划说明对齐协议3，消除旧固定阶段链和默认多稿的误导。

## 后续值得验证的方向

1. 用真实事项观察读者能否快速找到“目前怎样、改了什么、验了什么、还差什么”；再根据反馈调整结构，避免继续堆字段。
2. 规则层仍有多处重复。后续可单独评估按读取条件收敛，前提是轻量入口在缓存缺失时仍能保留必要授权与恢复边界。
3. 验证三宿主的重复初始化、克隆恢复、真实角色调用和业务闭环，逐宿主保留证据，不从模板或另一宿主推定通过。
4. 外部文档和 Issue 仅在具体任务授权后联调；配置、静态检查和本地完成不替代远端回读。

本轮只调整源码文档与模板。当前锁定安装继续使用原包；候选源码需另行发布和安装才会进入消费者项目。历史验证见 [验证索引](../verification/README.md)，其中的旧版本证据不自动证明当前源码行为。
