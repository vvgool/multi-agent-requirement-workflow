# 整体目标与路线

## 目标与实现边界

用户在 Codex、Claude Code 或 OpenCode 项目中初始化后，以自然语言发起或继续需求。协调主会话根据落盘进度派发产品、开发和测试角色，完成用户确认、实现、独立验收及修复，资料可随项目续改和共享。

采用统一角色源、角色专属 Skill、宿主适配和项目内状态；不增加独立 CLI、调度后端、跨会话并发或自动生产发布。角色职责见 [职责与工作流](agent-responsibilities-and-workflows.md)，具体执行规则以 agents/、skills/、workflow/ 为准。

## 当前组成

| 组成 | 当前能力 | 证据边界 |
| --- | --- | --- |
| 协调 | 状态路由、派发/恢复、交接、用户确认、索引 | 手动加载原型正常闭环已验证，原生完整闭环待验证 |
| 产品/开发/测试 | 各有入口 Skill、实际模板和阶段完成标准 | 已有隔离行为验证，不能替代真实业务验收 |
| 通用初始化 | 版本锁、本地忽略包缓存、Codex/Claude Code/OpenCode薄角色和共同入口 | 新适配文件格式与真实宿主激活分开验证；旧快照验证为历史证据 |
| 文档 | 本地及飞书来源、快照和审批摘要；产品需求正文受控写回 | 技术方案/测试报告仅本地输出，真实飞书待联调 |
| Issue | 可选已有 GitHub/GitLab Issue 绑定、目标授权、关键事件评论和恢复 | 默认关闭，静态及 15 个协议模拟通过，真实平台待联调 |
| 宿主适配 | 三宿主独立注册/派发/恢复映射，共用角色和Skill正文 | 原生调用及当前版本完整闭环均须在各宿主验收 |

## 框架共享与项目绑定

独立包统一维护角色、Skill和模板；项目提交workflow.lock.yaml固定真实包身份及可移植来源，完整框架放Git忽略缓存，按当前宿主及项目级信号选择目标宿主，各生成三个薄角色，共用必要入口；用户显式范围优先，逐宿主验证激活。推荐以 GitHub/Git URL 获取框架并锁定实际完整提交；manual来源保留离线手动包用途，不自动迁移旧锁。新机器补同版本；活动任务保留原版本，未知调用不因换宿主而重派。旧快照不自动迁移。权威契约见 [包规则](../../workflow/package.md) 和 [适配契约](../../workflow/host-adapters.md)。

## 需求与文档约定

- 需求目录以名称命名，内部 feature_id 稳定；同名独立需求另建身份。范围/验收变化或完成后续改建立新修订，保留旧证据并重新确认。
- 小需求默认需求稿、开发记录、测试报告三份；复杂开发再拆方案、模块任务计划和整体自验。执行模式按模块另选，文档档位不等于任务模式。
- 目标项目规则优先；无架构约定时按 Clean Architecture 做最小设计，不强加目录或无关抽象。
- 人从需求根 README 查看进度和有效文稿；执行记录、来源及 Issue 同步日志按需展开。
- Issue 仅作关联和留痕，不替代需求输入或审批；同步失败不回退本地业务。

目录、配置和审批细节分别由 [成果目录](../../workflow/output-layout.md)、[配置](../../workflow/config.md)、[文档规则](../../workflow/documents.md) 维护，不在规划中重复定义。

## 后续顺序与验收

1. 分别验证三个宿主的轻量初始化、重复与克隆恢复，再在真实新会话验证各自三个原生角色/所属Skill的实际调用，保存独立结果。
2. 使用当前布局跑用户确认→开发→独立测试完整闭环，并验证失败修复、等待和中断恢复不重复派发。
3. 分别联调真实飞书来源/授权写回，以及 GitHub/GitLab 绑定/评论/恢复；本地完成与远端同步分开验收。
4. 在三个宿主分别验证显式升级、版本一致性和失败恢复，再按需要补卸载；不从某个宿主推断其他宿主可用。

当前验证入口为 [验证索引](../verification/README.md)。早期设计/实施计划仅保留本地历史，不随当前源码分发，也不作为待执行计划；源码路径按当前框架定位，不引用作者机器位置。
