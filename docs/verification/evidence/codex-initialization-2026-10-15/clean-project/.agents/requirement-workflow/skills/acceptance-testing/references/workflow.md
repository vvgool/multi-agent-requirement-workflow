# 测试流程与结果判定

## 1. 理解交付并制定用例

读取批准需求和开发交付内容，确认目标行为、验收项、影响范围及可用环境。按任务中项目规则选择检查方法，既有用例只作为候选输入。

用例包含编号、关联验收项、前置条件、操作、预期及实际结果/证据。共用环境和前置条件写一次；局部需求用报告内的一张表即可。复杂用例单独编排，报告只汇总结果。

## 2. 核对是否偏离

结合源码/调用路径及真实执行，对齐以下内容，结论写入报告：

- 需求覆盖：已批准行为是否遗漏，是否有未批准规则或功能变化。
- 实现一致性：实际行为、接口和约束是否符合需求；开发报告是否与基线相符。
- 用例覆盖与预期：验收、必要异常、边界及集成是否有检查；预期是否来自需求，而非当前实现。
- 证据有效性：证据是否对应本次执行及待测基线，是否覆盖真实交付路径。

已确认需求下的实现错误记录缺陷；测试用例错误先在当前输出修正后重测。需求本身无法判断时记录问题/blocked，交协调层澄清。技术实现与原方案不同，但满足业务和接口约束时，记录差异及实际验证，不机械判失败。

## 3. 实际执行与回归

按用例执行适合项目的检查，保存必要的可复现步骤、命令及实际输出。修复轮次回归旧缺陷与受影响行为。静态、构建、替身、真实集成和设备等证据区分范围；不为凑层级重复执行，也不以局部通过替代必需全流程。

执行脚本、测试数据和缓存只写任务授权位置。缺环境、权限或人工检查待办如实记录，不绕过检查、不修业务代码。

## 4. 返回结论

先核对任务与代码仍对应当前待测基线，再判断：

| 状态 | 门槛与后续 |
| --- | --- |
| passed | 全部必验项通过，无未执行项、未解决缺陷/偏离/阻塞，证据与基线一致。交协调层记录完成。 |
| failed | 基线有效且已确认可复现的实现缺陷或违反批准需求的行为。提供关联验收项、步骤、预期、实际和证据，交开发修复；同时保留其他未执行项和限制。 |
| blocked | 基线/资料不符，或环境、权限、需求决策不足以得出完整结论且无已确认实现失败。说明已检查范围和解除条件，不将未检查项填通过。 |

基线在接单或执行中不符时优先 blocked；在旧基线上发现的问题可保留证据，但不能将其结论套用新代码。报告结果与 result.yaml 必须一致。
