# 存量方案通知兼容

仅处理已有任务含非空progress_path、已有development-progress.yaml/pending，或已有result.development_progress的run时读取。新任务不创建这些字段和文件。沿用该run原任务、包身份、实际路径与已有摘要；不回填或迁移历史。以下协议只用于完成原run，不作为新任务要求。

## 开发中方案通知

开发已获本版审批后，在首次实现代码修改前完成适用的可实施方案/任务及检查方法；简版一份 development.md，复杂架构/流程/关键接口升级完整版。完整版先交 technical-plan.md、implementation-plan.md，实际自验后再生成 verification.md，不预建空自验。当前 run 的执行身份、审批与写范围不因通知改变。

### 通知时机

首次可实施方案在改代码前提交并通知；之后仅在实现方案/接口/依赖或验收影响变化、出现需决策的阻塞，以及最终交接时更新文稿批次。常规任务勾选、同一方案内的修复尝试和检查输出留本run执行记录，集中到下一次必要通知时更新文稿，不逐任务刷新清单、摘要、README或额外派发。最终文稿仍须反映实际完成情况和完整自验。

同一角色续派优先复用原宿主Agent，传入新task及变化/缺陷摘要；每个run仍独立，接单重读当前task/status/审批及变化资料。未变化且在该角色上下文中已读的规则与模板可引用，不要求重复全文读取；上下文丢失、规则变化或适用性不明时重读。开发和测试不跨角色复用，不把开发自验当独立验收。

### 最小通知与单写者

开发在 task.output_dir 使用 [进度模板](../templates/development-progress.yaml) 落盘 development-progress.yaml；它是候选文稿版本的提交清单，独立于 task.result_path，不是 ready 或最终代码基线。必须带 feature_id、requirements_revision、run_id、role=development、task 的 framework（旧无锁任务按原实际身份）、document_version（本 run 从1单调递增）、kind（完整首稿 plan_ready、完整后续版 plan_updated；真实部分稿用 plan_partial）、document_mode（simple/full）、artifacts（kind/path/sha256）、execution（真实 status/summary/questions/block_reason）、previous_manifest_sha256（首次 null）。清单和文稿路径相对 output_dir，使用普通文件，禁止绝对路径、..、链接和跨 run；sha256 是实际原字节摘要。artifacts 只列实际可读的适用文稿，简版仅 development_record；完整版正常 running 必须 technical_plan/implementation_plan，自验后可加入 verification。

真实 needs_input/blocked 且完整版只有部分有效稿时，kind=plan_partial，artifacts 仅列实际已有的非空有效稿，missing_artifacts 明确缺少的 technical_plan/implementation_plan（与已有项互斥，合起来恰为所需两稿）；execution.summary说明缺口，needs_input 的 questions 非空且说明待决策及影响，blocked 的 block_reason 非空且说明解除条件。不得用 plan_ready 冒充完整、填空稿/占位稿凑数，或以放宽链接/摘要检查展示部分坏批次；已有稿不能链接尚未生成的缺稿或结果，应以文字说明未产出/尚未交接。无稿明确未产出，沿原结果回报，不造空稿或空部分通知。简版缺少可实施方案时同样不能冒称 plan_ready。完整通知 missing_artifacts=[]；部分稿解除后依据原宿主/结果路由补齐两稿，用更高版本 plan_updated，不能仅切换状态而保留缺项。展示不解除业务阻塞，不改变原 needs_input/blocked 最终结果及后续派发规则。

开发是候选文稿及清单的唯一写者，协调只读。第一次写入须不存在，或有本 run 的可靠拥有记录和已知摘要；仅文件名相同不是拥有证明。更新前核对当前清单原字节摘要及每个候选文稿与上次已知摘要一致，清单也含用户编辑保护；发现缺失、用户编辑、来源不明、符号链接或路径冲突，保留原内容和链接，暂停受影响操作并报告 blocked。用户编辑涉及需求/验收时交修订，不创建另一套方案绕过。协议依赖单开发/单协调且用户不并写候选；摘要核对不是操作系统级CAS，无法保证写入安全或存在外部并写时停止更新并说明限制。

### 完整版本提交与恢复

1. 同目录暂存完整新文稿及新清单，回读解析和摘要；保存最后已知旧摘要与新摘要。临时文件只能位于 task 授权 output_dir，不能用链接。实现调整同时更新相关图、模块、任务和检查，并在当前文稿记录原因及 AC 影响。
2. 原子写入 development-progress.pending.yaml 更新意图：同一任务身份、旧清单摘要或 null、新清单完整内容、每个受影响文稿的 path、old_sha256（首次 null）、new_sha256、staged_path；此文件是恢复证据而非可展示版本。写前存在旧意图时先恢复，不能覆盖。暂存命名和路径须可核实归属本次更新，引用相对 output_dir。
3. 替换前再次核对清单和目标旧摘要；按意图用同目录原子替换逐份文稿，全部符合新摘要后，最后原子替换 development-progress.yaml，回读核对，再清理完全匹配的本次意图及未引用暂存。多文件替换不具备整体原子性，清单是批次提交点。相同内容可保持原文件，勿碰未授权位置。
4. 中断后先核实原活动调用；开发恢复意图时，每份目标只能为意图的 old 或 new 内容，old 目标须有匹配 new 的暂存才可补完，new 目标可保留。清单只允许匹配旧摘要或完整新清单摘要；全部 new 后可提交/确认新清单。目标缺失仅在 old_sha256=null 时合理；其他内容/缺失/身份矛盾或无法确认归属时 blocked，保留证据，不盲目覆盖。提交已完成但意图未清理时核对相同 new 内容后补清理，不增加文稿版本或创建新 run。

### 通知与执行分离

清单完整提交后，用当前宿主真实可用消息/通信工具通知协调，传真实清单路径及其 SHA256、任务身份、文稿版本与可读文稿链接；不另写一份通知正文报告。正常通知后原 run 立即继续实现，不等待技术批准或展示回执。无即时能力时保留持久清单，使用可用查询/转达，明确尚未展示或能力限制；不能谎称已发送/已展示，不为等回执主动结束或重派任务。实质业务决策 needs_input、范围变化走修订、能力/权限/文档一致性不足 blocked，仍沿原最终结果契约处理；通知里的执行状态不能替代最终结果。

### 协调消费

协调收到消息或恢复/查询运行中任务时，在保持原活动任务的前提下消费通知，不因通知清空 active_run、改变 stage、增加开发次数或再派角色。先核对 task/status 的当前需求、修订、run、框架和有效审批；旧 run 来件只留存，不覆盖当前入口。根据实际 output_dir 定位清单，旧无通知任务不生成虚假通知。

读清单A原字节并核对身份、schema、版本、字段、路径和内容摘要，再读全部文稿核对sha256并验证链接，最后重读清单B；只有A=B且所有已列文稿匹配、非空且无未替换模板占位符，kind/执行状态/必需稿件集合与缺项满足上述契约，才是可消费的完整提交批次。plan_partial 的批次完整不表示方案内容齐全，必须标明“部分方案，未验收”及缺项、问题/解除条件；不能提升为完整 plan_ready。有 pending 意图、摘要不匹配或读取变化时不展示混合内容：重读最新已提交稳定版本，仍有意图或不能稳定核对则报告展示待恢复/blocked及具体位置，保留原索引，通知开发检查；不代写候选或恢复其意图，不假称开发已停止。消息摘要与现清单不同，若现版可靠更高则消费现版；同版不同摘要为冲突，不用旧消息覆盖。只能核实部分文稿时也不能冒称完整方案就绪。

按 [成果规范](#开发中候选展示) 安全更新对话及 README：同身份、版本及清单摘要已展示则幂等返回；未完成展示可补办，不重复建任务/复制正文/推进阶段。记录真实展示结果及文稿来源摘要，开发实施与展示进度分开。已有正式稿/README摘要不符也先停止覆盖并报告冲突。最终 ready 前开发复核图、模块、任务、AC与实际实现；按下节完成最后通知与结果，协调再沿原规范固化，独立测试门槛不变。

### 最终交接与摘要收敛

最终文稿不引用内部结果或清单，关联由result单向维护。全部必需检查完成后：

1. 先补齐最终实现、可读代码版本与验证事实，按完整版本提交协议提交末次文稿和清单；内容已完全一致时复用该清单，不为交接另增文稿版本或通知。
2. 再以已提交文稿的真实摘要、末次清单指针及已验证代码基线一次生成result.yaml，按已有拥有记录保护用户编辑并原子落盘；回读核对任务/审批、源码基线、全部文稿摘要和无pending后，发送最终结果及清单指针。末次文稿须在result.artifacts中以相同kind/path/sha256出现；无需先写一份结果再刷新。

协调核实宿主结束后再读取最终结果，并在同一次交接核对清单、文稿摘要和基线；若该清单已在本会话核对展示且文件未变，只核对未完成的交接项，不重复展示方案。未展示的末次方案与最终交付合并说明，不额外发一轮进度通知或更新README。

任何缺项、摘要/链接差异、源码变化、pending或用户编辑冲突仍拒绝推进。中断先查原调用并按已知摘要恢复，不因结果缺失重派；旧顺序已生成的中间result仅按已有记录收敛，不删除、覆盖或重造历史。旧无通知任务沿原契约，不补造通知。

## 开发中候选展示

原子提交、身份、摘要与双读检查以 [通知契约](#开发中方案通知) 为准。开发正常通知后继续同 run；协调收到通知即处理，不能等最终 result 才首次展示。候选仍在 task.output_dir，不复制到 documents/，不另造方案正文；布局1按原task/output/artifacts路径读取，不搬迁历史、不补造旧通知。

核对完整版本后，在当前对话提供真实可读候选链接，标明“开发中方案，未验收”、修订/run、document_version及来源摘要；需求 README 只写方案状态、文稿版本及必要缺口，不链接本机候选、结果或清单。简版一份记录，完整版适用方案/计划，自验存在后才链接。既有正式开发/测试成果标“上一基线，当前待重验”，不能与候选混成当前正式交付。needs_input/blocked也展示已存在的稿件、缺口及解除条件；full部分稿须为契约允许的plan_partial，标“部分方案，未验收”，不要求缺稿存在、不链接缺稿、不放宽已列稿的整批稳定/摘要/有效链接检查；无稿明确未产出，不生成空成果。

协调以根 artifacts 的 kind: development_progress 记录当前已核对版本：path（清单相对需求目录）、revision、run_id、document_version、sha256（清单摘要）、documents（每项kind/path/sha256，路径相对需求目录）、display_status（pending/displayed/blocked）及实际原因，按 [状态规则](#开发方案展示状态) 维护；该项只是显示来源索引，不能代替代码基线或最终result。先保存pending来源，再安全更新入口及对话，确认实际展示后才记displayed；中断可补未完成展示，同版本已展示不重复处理成新任务。若入口已更新但显示状态未保存，先核对入口已知摘要与同版本内容再补状态；无法确认时保留内容并报告，不覆盖或猜成功。

README沿原 feature_index 拥有摘要规则检查，正式文稿沿原固化摘要规则检查。用户编辑或来源不明时停止覆盖、给出冲突位置及可读链接，记录展示blocked，不把其等同开发停止或成功。协调不同时写候选；开发清单过期或内容半更新只重读/请求开发恢复，不能索引未提交版本。最终ready须先核实宿主结束，按本文件的最终交接收敛顺序一次检查末次清单、development_progress指针和最终artifacts摘要一致；已核对且未变的展示批次复用记录，末次方案展示与最终交付合并；未收敛不得固化。核对通过后，再按“固化正式成果”复制、重定位链接及保存来源；通知清单/恢复意图只留run证据，不当正式正文。开发结束后再有冲突也先保护用户内容，不能以最终结果绕过摘要检查。

## 开发方案展示状态

运行中方案按 [通知契约](#协调消费) 与 [候选展示](#开发中候选展示) 消费。只新增/更新 artifacts 中 development_progress 的显示来源元数据及状态；stage、active_run、development_attempt和审批保持真实业务事实。每次显示元数据持久化也执行 state_version 比较、递增、回读、事件及入口同步；事件记 development_plan_display_pending/displayed/blocked，附run、版本、清单摘要与实际原因，不伪造实现完成或最终ready。

同一run更高版本才可替换当前显示来源，相同版本相同摘要只恢复未完成展示；相同版本不同摘要、用户修改README/正式稿、未知任务身份或索引矛盾先保留并报告阻塞。展示blocked与实施进度分开，不能凭展示失败更改开发真实执行状态；若开发回报needs_input/blocked则按原结果流转并展示已有方案。plan_partial展示记录保留execution、missing_artifacts及真实问题/解除条件，仅表示已列批次通过检查，不表示方案完整或阻塞解除；running/full缺稿不能展示为就绪。旧通知只留存，不覆盖较新版本；已提交版本显示中断按原更新恢复规则补办，不重复派发。任务未知先查原调用，不能通过创建新run解决展示问题。最终正式固化后入口以最终结果为准，保留原候选来源和展示证据。
