# 阶段路由

## 接单判断

用户明确“新需求”即协调接单，未命名先收集目标确定名称。后续补充沿用需求，除非用户明确取消/切换/退出；目标是框架文件不改变角色边界。单纯问答/审查可只读答复，未进入流程的独立维护才适用维护例外。协调可定位交接，阶段分析/实现/验收交实际原生角色，不自行代做。

## 决策顺序

1. 重读status，核对事项/修订/协议；未知组合或矛盾blocked。协议1用原锁定包路由，不迁移。
2. active_run非空先查询/等待/重连，unknown不重派。新输入记入input待处理，保留活动身份。普通方案通知只读展示，不清调用/推进。
3. 同目标未完成的范围/验收新增按[增量契约](incremental-changes.md)原目录回产品重审；保留任务及额度，旧审批/结论不能推进新范围。waiting_user处理原问题或pending_review；只有当前正式评审明确回复才批准。blocked先核实解除条件，“继续”不代替。
4. Issue功能默认停用；启用或有历史待处理才读[Issue规则](issue-tracking.md)。外部写入仍须授权，策略不代替业务审批。
5. 无活动调用且允许执行时按表续接既有角色任务；先按[包复用](package.md#会话内核验复用)与[宿主映射](host-adapters.md#业务派发和恢复)核对环境，再按[交接](handoff.md#派发)启动。

| stage | 动作 |
| --- | --- |
| draft | 续产品澄清/产稿；独立Bug入口续bug boundary |
| requirement_review | 展示当前需求或Bug边界，待明确确认 |
| development | 有当前baseline_id及review_digest审批、无未处理范围变化且额度允许后续原开发/Bug任务 |
| testing | 续testing，绑定当前批准baseline_id/approval_digest、具体交付及精确代码基线 |
| completed | 展示证据；新变更建新修订 |

## 产品澄清答复

按[澄清交接](handoff.md#澄清记录与再次派发)轻记录。累计输入存在冲突/依赖变化/待分析则续原产品；答案齐全且尚未整理才续一次产稿；部分有效答案且剩余问题有效则等待。已覆盖输入接续结果交接，重复答案不派调用；有active_run先核实，不并发。方向认可不算正式审批，过时ready不得评审。

## 交接核对

协议2执行[最小交接核对](continuous-tasks.md#最小交接核对)：核任务/调用/交付/输入授权/审批/摘要/基线，不重复角色内容自检。缺必需项blocked；宿主ended不代表业务ready。核对后同一次固化及状态/索引更新，阶段规则见持续任务契约。普通失败默认原开发修复，专门诊断才走[Bug](bugfix.md)。新修复保留原任务、新交付及共享attempt，不能靠新任务绕额度。

## Issue 生命周期钩子（启用时）

真实派发、交接、人工批准、等待/阻塞变化及已核实发布/回滚的业务事实先按state-contract保存；再按Issue规则事件表生成唯一快照并调用支持Skill。开发/测试开始须实际调用已核实，失败后的下一次实际修复才记repair_started；unknown不伪造开始或失败。completed只表示技术独立通过；manual关闭另需本次用户最终完成确认、目标范围关闭/必要摘要许可，发布仅按批准完成条件适用，after_release保持严格。completed不等于发布/关闭；有运行机会时按生命周期契约核对已授权关闭与未决操作，故障不阻止业务继续。无新事实不新增事件。
