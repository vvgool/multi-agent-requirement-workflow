# 阶段路由

协调 Agent 依据刚读取的 status.yaml 选择下一步。各阶段完成标准由对应角色指向的 Skill 定义，本文只定义派发与状态迁移。

## 接单判断

1. 用户明确说“新需求”即进入协调接单；尚未给名称时先收集目标、确定可区分名称，再按修订规则创建需求状态和产品任务。接单澄清期间保留用户原话及后续补充，未命名不意味着退出流程。
2. 后续说明、补充、优化和对当前需求的修复沿用原需求上下文。修改对象属于框架规则、Skill 或模板不改变路由；仅用户明确取消、切换需求或要求退出流程，才改变上下文。涉及范围或验收变更仍按修订规则办理。
3. 直接维护例外仅适用于未进入需求流程的独立请求，或用户明确退出流程后要求直接维护。针对当前需求的问答、状态查询和只读诊断可由主会话直接答复，保留需求上下文，不因此推进阶段；诊断后的实现或修复继续按需求路由。协调层可以检查文件以定位和交接，但需求阶段的分析、实现及验收由原生角色执行。
4. 每次接单先说明当前动作属于接单澄清、阶段派发或独立维护及其依据。尚未派发时如实说明，不把读取角色文件或主会话编辑视为 Agent 执行。

## 决策顺序

1. 核对需求身份、版本和状态。已有状态缺失、未知或矛盾时阻塞核查。
2. active_run 非空先查询、等待或重连；期间可按 [协调消费](execution-contract.md#开发中方案通知) 处理同 run 的开发方案通知，仅展示已核对完整版本，不将其视为最终结果、不清任务或增加调用次数。prepared/unknown 先核实调用是否发生，即使 execution_status=idle 也不能重复派发。
3. waiting_user 先处理原问题或 pending_review；只有对应当前评审的明确回复才算批准。
4. blocked 先验证解除条件，普通“继续”不能清除阻塞。
5. Issue默认关闭且无历史待处理记录时跳过；已启用、用户明确改变关联策略或需恢复既有记录时，才读 [Issue规则](issue-tracking.md)，在无活动任务的派发前处理前置绑定。已有选择按策略复用；required 未满足时不派发业务角色，保留当前 stage。同步失败不作为业务 blocked 条件。
6. 无活动任务且允许继续时按下表执行。每次状态变化后重读并重新决策。

| stage | 动作 | 角色 |
| --- | --- | --- |
| draft | 首次派产品；已有待答问题按下节判断是否转达、重新分析或整理文稿 | [产品](../agents/product-agent.md) |
| requirement_review | 展示需求并等待用户明确确认 | 协调层转达与记录 |
| development | 派发实现或修复，携带已批准需求和已有缺陷 | [开发](../agents/development-agent.md) |
| testing | 派发验收，携带已批准需求和待测开发基线 | [测试](../agents/testing-agent.md) |
| completed | 展示完成证据；优化按修订规则创建新版 | 无派发 |

派发前按 [包规则](package.md#会话内核验复用) 核对锁定版本、缓存、初始化pending及当前宿主真实激活；符合条件时复用本会话已核实的环境结果，再按 [适配映射](host-adapters.md) 检查实际角色文件和宿主能力，缺失分别记录 role_not_available（含 required_role）或 host_delegation_unavailable。development/testing 须有本版有效审批，testing 还须有开发基线。审批已保存但阶段迁移中断时，核对有效性后补完迁移。

## 产品澄清答复

本节用于 draft 阶段的产品待答、用户补充及恢复；先执行上文决策顺序。已有 pending_review 按正式评审处理，改变已批准范围按修订规则处理，不能用澄清答复替代审批。协调层只依据产品给出的依赖、适用条件和已有材料判断转达，不新增业务规则或方案。

先按 [产品交接](handoff.md#澄清记录与再次派发) 保存问题、选项、推荐、用户原话及对应关系，再核对累计输入、待处理标记、此前派发和适用产品结果，恢复尚未完成的分析/产稿决策，然后按以下顺序选择唯一动作；判断依据是累计回答内容与依赖，不是最新消息是否重复或已答数量。仅保存答复、作出派发决定或准备 task 不代表已完成处理；已有调用按活动任务规则核实，已有适用结果则接续其交接/评审，不重新派发同一已完成动作。调用或处理证据矛盾、无法核实时先阻塞核查。

| 优先条件 | 动作与完成条件 |
| --- | --- |
| active_run 的 prepared/unknown/running 尚未确认结束 | 保存新答复为待处理，查询、等待或重连原任务；保留活动任务及真实执行状态，不创建第二次调用。确认结束并核对结果是否覆盖最新输入后，重新判断累计答复；过时的 ready 不能直接提交评审 |
| 累计输入中尚未处理的答复改变其他问题前提/范围/方案，存在冲突/歧义，新增诉求需查源码/新分析/新方案，或无法可靠判断这些答复后剩余问题有效性 | 无活动任务时派一次新产品 run 分析，携带触发原因、累计问题/答复和必要来源；由产品保留有效结论、更新缺口。旧结果无依赖说明且现有依据不足时亦走此分支，不伪造历史依赖 |
| 所有当前问题均被有效回答且无未处理依赖，尚未由适用产品结果完成整理 | 派一次新产品 run 整理需求和验收，包括最后答复已保存但派发前中断的恢复。产品重读累计输入，信息充分直接产稿，有实质新缺口才提问；ready 后仍展示本版文稿等待正式审批 |
| 仍有有效未决问题，且无待处理变化、分析或产稿动作；最新为空回复、无新信息的重复答复或未解决当前选择的含糊“继续” | 不派发、不替用户选推荐，保持 draft/waiting_user，按需重示当前有效未决问题。明确选择本轮仍有效建议才记为有效答复 |
| 仅要求重述或解释已有选项，已有材料足以直接回答，且无待恢复的分析/产稿动作 | 依据原内容解释、保留推荐及依据；不增加方案或代选，保持 draft/waiting_user，不派发。材料不足需分析时走重新分析分支 |
| 仅部分有效回答，已有依据能确认剩余问题仍有效且无依赖待处理 | 保存答复，转达有效未决问题，保持 draft/waiting_user，不新增产品 run |

首次尚无产品问题时按常规派发。仅实际新调用使用独立 run；复用同一产品 Agent 不复用 run。每次不派发也记录依据及可恢复位置，见 [状态规则](state-contract.md#无新-run-的澄清更新)。

## 结果到状态

| 当前角色 / 结果 | 下一状态 |
| --- | --- |
| 产品 ready | 按 [成果目录](output-layout.md) 固化角色提供的需求稿，展示后 requirement_review/waiting_user |
| 产品 needs_input | draft/waiting_user，转达具体问题 |
| 用户批准当前评审 | development/idle |
| 开发 ready | 保存角色提供的 development_baseline，testing/idle |
| 开发 needs_input | development/waiting_user，转达决策问题 |
| 测试 passed，全部验收完成、无未解决缺陷且基线一致 | completed/idle，归档报告和证据，不自动发布 |
| 测试 failed | development/idle，携带失败报告；次数用尽则 blocked |
| 任一角色 blocked，或调用/权限/身份/必要证据异常 | 保持当前阶段，execution_status=blocked并记录原因、解除条件 |
| 任一角色 stale_task | 按 [执行契约](execution-contract.md) 处置过期来件，不推进当前阶段 |

## 交接核对

旧修订/run来件或stale_task先按 [过期任务](execution-contract.md#过期任务) 留存处置，不套用当前交付门槛，不清除其他活动任务；旧无锁/旧布局仍按原契约核对。

协调层在宿主确已结束后，读取原task、host及result，一次核对：当前身份/修订/run和框架绑定一致；开发/测试的本版审批有效；必需字段、文稿及证据存在且路径授权、摘要与内容一致；结果状态和所声明完成项无矛盾。结果状态要求基线时，按 [基线契约](code-baseline.md) 核对本轮实际文件未变；测试另核对原开发绑定。产品正文和质量检查完整性按 [产品结果](handoff.md#产品结果) 核对。

内容质量由执行角色负责：产品判断需求/验收质量，开发判断方案与自验，测试独立执行验收。协调实际读取交接材料以核对上述条件、转达用户并固化文稿，不重复业务分析、逐条质量自检或重跑测试，也不为交接另写审查报告。缺项、矛盾、摘要/基线变化时保留现场，交责任角色补证或修正；不能仅凭declared status推进，也不能替角色补写通过结论。

同一次交接中已核对且未变的材料可直接用于固化和状态更新，不在各步骤重复执行完整检查；写入前的拥有摘要/状态版本检查仍执行。中断恢复、文件/源码变化或上下文丢失时重新核对，不把复用记录当新证据。旧版或旧run结果仅留存，不能清除新active_run。

范围变化须先确认旧任务结束，再按修订规则归档旧版并进入新版draft/idle，重新评审；completed的历史记录保留。

需求决策阻塞时，协调层转达原问题并记录实际答复；仅引用已批准内容即可解除的，核实后恢复原阶段。需要补充或改变已批准正文/验收时按修订规则建新版 draft，重新由产品整理评审；不把未批准的新规则交给开发或测试继续执行。

## 交接与次数

产品使用 [产品任务](../templates/product-task.yaml) 和 [产品结果](../templates/product-result.yaml)；开发/测试使用 [角色任务](../templates/role-task.yaml) 和 [角色结果](../templates/role-result.yaml)。按所选角色文件填写 completion_criteria；任务 approval_digest 取 approval.review_digest。测试绑定 development_run_id 和 development_baseline，按 [代码基线契约](code-baseline.md) 核对；修复任务附 defect_report_path。

开发次数按修订版累计，默认 max_development_attempts=3，包含首次。实际发起新开发调用前增加一次并绑定 run；角色/宿主缺失不增加，未知调用恢复不重复计数。达到上限后 development/blocked、development_attempt_limit，等待用户调整或决策。

同一宿主 Agent 只在同一角色内复用。有新输入、状态变化、真实调用或交接时，在已有记录保存动作与依据；无变化的轮询和重复展示不新建决策记录。状态、历史、审批和范围变更分别遵循 [状态规则](state-contract.md)、[修订规则](revisions.md) 和 [文档规则](documents.md)。
