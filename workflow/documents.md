# 文档与来源

一次性局部低风险小修直接完成。需要持久跟踪时保留一个 [事项协调入口](output-layout.md)，按下述分工维护相关文档。已有需求、设计或验收文档按职责引用，保留项目原路径和格式；已有入口可继续使用，无需复制一套同名文件。外部正文和参考资料按需读取、注明来源，不覆盖只读来源。

## 按复杂度选择文档

先根据业务规则、模块边界、权限风险、持久状态和协作依赖判断产物，不按文件长度、代码行数或角色数量凑文档。

| 情况 | 文档选择 |
| --- | --- |
| 一次性、局部低风险小修 | 在会话中直接完成 |
| 目标清楚、方案局部，但需要持续跟踪 | task.md 可合并目标、验收和必要方案 |
| 跨模块且有独立业务规则、多种权限边界、持久状态/恢复，或多个实施单元需协调契约 | 在实施前分别形成或引用 requirements.md、technical-design.md；按依赖拆出 implementation-plan.md |
| 验收跨模块、环境或包含多项权限/恢复场景 | 验收时维护 verification.md，区分实际检查与未执行项 |

复杂需求主动按职责拆分，不等 task.md 膨胀后才拆。多角色本身不触发全套文档。新增文档的条件是需要独立维护该类决策或证据；只创建有实际内容的产物。

## 复杂需求的内容质量

复杂需求的requirements.md应形成PRD；起草或续改前读取 [需求Skill](../skills/requirement-analysis/SKILL.md) 及其PRD模板和产品设计方法。技术设计与实施拆分读取 [开发Skill](../skills/feature-development/SKILL.md) 及其方案与拆分方法和模板。当前会话可承担这些职责，不强制另派角色；一次性局部低风险小修保持直接完成。

模板约束适用内容，已有项目格式可以映射使用。起草者在提交或实施前核对覆盖情况，删节说明原因，清除占位符；已有文档也按此标准补缺。不能把“读过模板”“文件已创建”或“标题齐全”视为内容达标。

- PRD：问题、角色、目标与完整旅程清楚；复杂规则适用时，核心术语、状态、不变量和业务责任主体可追溯；功能有稳定编号及可判定验收；关键异常、权限和适用非功能约束明确；用户要求、Agent建议和待决假设区分。
- 技术设计：模块有职责、数据拥有者、显式契约和依赖；核心旅程跨模块可闭环；重要方案取舍有依据。
- 实施计划：功能/验收映射到可独立交付和验证的任务，消费与产出契约一致、文件归属明确、前置条件可满足，尽早验证业务闭环并保留整体集成检查；代码或契约变化时同步调整受影响计划和验证范围。

自检发现、修正和阻塞写回对应文档末尾，不新增审查账本。影响关键行为的未决解决前，受影响实施保持待定；可独立推进的范围明确列出。复杂需求按 [实施与完成门槛](execution-contract.md#实施与完成门槛) 必须完成实施前独立审查和最终独立验收；另一适任角色按上述内容检查，并沿实际行为核对，而非仅查目录和标题。确认沿用执行约定，已授权范围不因检查或文档切换重复审批。

## 内容归属

| 文档 | 维护内容 |
| --- | --- |
| task.md | 简短目标、当前状态、实施任务勾选、依赖、负责人/写入归属、阻塞、验证摘要及文档链接 |
| requirements.md | PRD：问题与目标、角色旅程、（适用时）领域模型与业务语言、产品方案、功能规则、适用非功能要求、验收标准及业务决策 |
| technical-design.md | 现有实现依据、模块与接口、数据及状态、授权与信任边界、失败/恢复、兼容及技术取舍 |
| implementation-plan.md | 可交付实施单元、依赖顺序、文件归属、输入输出、检查方法及集成安排 |
| verification.md | 验收对象、环境、实际结果、证据、缺陷和未验范围 |

当前进度只在 task.md 更新；需求和设计正文各自维护有效结论，task.md 只摘要并链接。已拆出需求时，完整验收标准只维护在需求文档；计划引用相应标准，验证文档逐项记录结果，不复制第二套预期。正文中的未决问题放在所属文档，影响推进的阻塞由 task.md 摘要引用。

一个事项可包含多个可独立核对的实施任务。复杂实施在计划中明确每个单元的范围、依赖、负责角色/文件写入归属、交付及验证方法，task.md 按单元跟踪状态。确需委派时才建立对应原生任务；文档拆分不要求另开事项，也不为每个单元复制整套需求。只有独立业务目标才新建事项。

## 实施计划与任务进度

实施计划定义任务怎么做，task.md 记录任务做到哪。采用实施计划时，两处按同一实施单元编号（如 T1、T2）对应；编号在事项内保持稳定，后续新增或细拆不重排已有编号。

- 计划维护范围、依赖、文件写入归属、必要步骤、交付条件和验证方法；task.md 每项只列编号、名称、当前状态及计划章节链接，按需要摘要负责人或阻塞。
- 按可独立交付和验证的单元拆任务。单元内部的文件修改、命令及操作步骤留在计划中；需要独立交接、管理依赖或验证时，才拆成 T4.1、T4.2 等子任务，并在 task.md 对应跟踪。每个单元至少明确输入、产出、文件写入归属、完成条件和验证命令；不把“创建文件”本身当作完成条件。
- 完成条件在计划中定义，完成事实在 task.md 记录，实际证据由验证文档或原检查结果提供。开发完成而必需验收未通过时，保持未勾选并注明待验或失败；父任务只有在必需子任务及集成检查完成后才勾选。
- 计划必须落实执行约定要求的独立验证等交付门槛，不能把必需检查缩减为开发自验。可把独立验收列为单独的实施单元，也可纳入相关单元完成条件；对应待验任务在 task.md 保持未勾选，不能只在正文写“独立验收未执行”却把全部任务勾完。验收发现缺陷时记录修复与复验待办，满足必需门槛后再完成。
- 新增或调整实施单元时同步计划和 task.md 的编号、名称及链接；日常进度只更新 task.md，实际检查结果更新验证文档。计划不维护第二套勾选或执行状态，小事项无需为编号建立实施计划。

## 变更与确认

补充、修复和普通继续更新同事项中受影响的原文档及任务状态，重要范围变更注明结论和影响。拆分已有长 task 时迁出对应正文、保留链接，保持已确认结论、未决项及原证据有效范围，不重跑需求澄清或重新批准已有授权。

范围或验收分歧先在对话中确认，具体风险按 [执行约定](execution-contract.md) 处理。项目规则决定推进方式；通用 Skill 只补充适用的方法，不因创建文档、切换角色、进入下一实施单元再叠加另一套审批或执行方式选择。新风险和新范围仍须确认；未知外部写先查原调用，不重放。外部写入须有具体目标、范围和实际权限，读取链接或配置均不替代授权。

## 读取与交接

从 task.md 获取当前结论和下一步，再按本次职责读取相关需求、设计、计划或验证段落及代码。交接传入口、实施单元、允许改动范围、已验、未决及必要原生引用。安装回执、完整哈希清单和日志在本地完成检查，向模型只返回结论、异常和证据位置，避免反复全文回显。

共享文档只写目标、决策、实际结果及必要引用，不写凭据、重复机器身份或完整日志。旧审批及来源快照按原锁定包保持原字节。

## 人读文档格式

面向人的 Markdown 文档按以下顺序组织，打开文档即可从上到下理解当前结论：

1. 标题后先用一两句话给出当前结论；需要比较多个短字段时才用摘要表。日期、负责人、范围外事项等信息仅在有助于理解时保留，未知事实如实说明。
2. 按文档职责组织正文：需求写目标、范围、规则及验收标准；设计写依据、方案、边界及技术未决；计划写实施单元和依赖；验证写对象、检查、证据及限制。简单事项可以合并小节，保持“先结论、后细节”，通过引用衔接其他职责内容。
3. 验收标准应说明可判定的预期结果；实际验证使用短表格或列表，写明状态：`通过`、`失败`、`未执行`、`阻塞`或`不适用（原因）`。不能用空白、默认勾选或“已完成”代替证据。
4. 占位内容统一使用 `[待填写]`、`[不适用：说明原因]` 等明显标记；模板说明放在 `> 填写提示：` 引用块中，实例化后删除提示。
5. 按上文内容归属维护正文，task.md 只汇总当前进度和必要链接，方案与证据放在对应文档。
6. 表格只承载短字段和结果，长说明放在表格下方；代码、日志和外部资料使用链接或短引用，不把完整日志粘进正文。

这套格式只约束人读 Markdown 的表达，不新增 status、result、events 等机器账本，也不要求每个角色都生成全部文档。模板按需使用，task.md 仍是唯一协调和进度入口。

## 图示与代码块

能用图更清楚说明的关系优先用图表达。先给结论，再放图，图后只解释关键边界和取舍，避免用长段落重复逐个描述节点。

| 要说明的内容 | 优先表达方式 |
| --- | --- |
| 业务步骤、分支、异常处理和修复流程 | Mermaid 流程图（flowchart） |
| 模块职责、分层、依赖与系统边界 | Mermaid 架构图（用 flowchart 的 subgraph 分组） |
| 跨模块调用、请求响应、异步回调与重试 | Mermaid 时序图（sequenceDiagram） |
| 状态及触发条件 | Mermaid 状态图（stateDiagram-v2） |
| 接口定义、请求响应、配置、命令和必要代码片段 | 带语言标识的代码块，如 typescript、json、yaml、bash |
| 字段对照、方案比较和检查结果 | 短表格 |

涉及流程时优先给流程图，涉及模块边界或依赖变化时优先给架构图；同一事项按实际内容选择，不为凑齐图型生成空图。简单事实或一步操作仍可用短句。复杂图按业务路径或模块拆分，节点写职责或动作，箭头标明调用、数据或判断条件。

图示区分现状与拟议方案，代码块区分真实片段与示意。依据来自已读取的实现或已确认方案，未知关系明确标注；模板中的示意节点必须替换或删除，不能作为实际实现证据。图中引用的文件、接口及相关证据应在图的附近提供链接，改动后同步更新受影响的图。

代码块保留可理解的最小上下文，标明用途；命令注明工作目录和前置条件，请求响应标明关键字段与异常。多步命令按实际顺序列出。完整源码和日志通过链接引用，平台无法渲染 Mermaid 时按交付需要提供可查看的导出图或简短文字说明，保留可编辑源。
