# 测试先行与行为证据

开发和Bug修复实施前读取；测试角色检查其证据。适用性取决于行为能否用有意义的自动化检查约束，不取决于任务大小。流程选择见 [路径选择](routing.md#路径选择)，独立审查和交付条件见 [实施与完成门槛](execution-contract.md#实施与完成门槛)。

## 默认方式与例外

业务规则、计算、权限、状态转换和接口行为默认TDD。并发、幂等、持久化及跨模块行为使用适当的集成或契约测试，不能仅靠内部函数测试证明闭环。可稳定复现的代码Bug在修复前锁定失败行为，已有失败测试可以直接复用。

纯重构先确认已有行为测试有效，补足关键缺口，再保持测试通过；无需为未改变的行为制造失败。文稿、素材、纯视觉、探索原型和生成产物使用适合的检查：说明不采用TDD的原因、替代验证和限制。生成产物优先检查生成源和可观察结果，手写业务源不因输出由工具生成而豁免。设备、外部宿主或缺少环境时，先验证可测逻辑，明确阻塞及真实环境待验项，不能把环境缺失算作成功或功能RED。

例外在已有任务或交接中简述，不新增审批或专用报告；范围与具体风险仍按执行约定。低风险可逆文稿和无行为价值的镜像检查不新增测试。

## 单个行为的开发循环

1. 从验收选择一个行为，写或复用最小有意义的测试，检查用户可观察结果而非复制实现。
2. 实际执行，确认RED由目标行为缺失或错误导致。语法、依赖、连接或测试装配错误先修正；若意外通过，核实已有行为与测试有效性，不伪造失败。
3. 在允许范围做最小实现，执行同一检查确认GREEN，并运行受影响的相关检查。
4. 必要时重构，保持测试通过，再选择下一个行为；避免先写完所有测试再批量实现全部功能。

根因不明的Bug先取证和验证假设，再用回归测试约束修复。已有实现不为补做TDD删除重写；实现后补的测试如实称为回归测试。

## 实际证据

计划写行为、拟执行命令、前置条件和预期失败；实际结果记录到原验证文档或交接消息，包括测试/场景、命令或操作、实际RED原因、GREEN结果及相关回归。日志引用已有位置，不能把计划或开发者口述当作已执行证据。

TDD不代替产品方案、独立审查或整体业务验收。测试角色核对测试与需求是否一致，区分读取证据、重新运行和真实环境操作；无RED证据时明确未证明TDD，不能仅凭当前全绿倒推先前执行顺序。
