# 复杂需求的方案与拆分

复杂需求设计、拆任务或继续修改前读取，写文档时再读相应模板。按 [人工确认](../../../workflow/execution-contract.md#人工确认) 核对当前需求是否已获批准，再检查PRD的业务流程、功能规则、验收标准和待确认问题是否清楚；有文档不等于可以开始设计。缺少关键业务决定时，按需求分析Skill补齐；依赖这个决定的工作暂停，不受影响的工作可以继续。

## 设计模块，再拆实施任务

产品功能回答用户能做什么，技术模块回答谁负责哪些规则和数据，实施任务回答按什么顺序交付和验证；三者通过编号关联，不要求一一对应。

1. 沿真实代码入口和调用链识别可复用能力、改动点及外部能力限制。没有核实的SDK/平台能力明确待查，先验证会影响方案的约束。
2. 对会影响模块边界、数据归属或交付成本的重要选择比较可行方案，说明推荐理由与代价；唯一合理方案说明依据，不为局部实现细节凑备选。
3. 模块分析是复杂需求的必需步骤，新增模块不是；复用现有边界时说明足够承载本次行为的依据。按业务职责、数据/状态归属和变化原因确定模块边界。每个模块明确负责和不负责的内容、拥有的数据、对外契约、依赖及验证边界。优先复用稳定约定，避免仅按页面、文件夹、技术层或角色数机械拆分。
4. 用架构图说明模块职责、状态由谁管理及模块间依赖，用业务流程的时序图核对调用、状态写入、外部操作和返回结果；已有适用图直接引用，不用长段落替代关系图。每份可变状态明确由谁负责，模块间按接口定义协作；发现职责重叠、循环依赖、同一数据被多处修改或调用层次混乱时先调整设计。共享文件仍单写。
5. 明确跨模块输入输出、错误语义、状态转换及版本约束。接口使用项目实际类型/签名或请求响应示例，规划中的路径和接口标为拟新增，不伪装成现有能力。异步/持久状态按风险说明超时、重复、并发与未知结果处理。

对跨模块、公共契约、持久状态、迁移、多方案，或重复失败且已有证据指向契约、状态归属或架构边界问题的设计，使用以下轻量提示，不建立阶段状态：先取证真实模块、调用链、状态和已有约束；再形成最小方案并记录必要取舍、契约和验收方式；实施中若有具体新证据证明原契约或方案不成立，再重新判断设计。明确局部小修不使用该提示。

## 表示范围与复合失败

涉及公共数据的转换、编码、持久化或输出时，沿公开输入→转换/编码→存储/比较→输出核对值域、精度和单位，确认每层表示都能承载已确认契约。依赖的默认限制不能无声收窄允许范围；业务范围未定先澄清，范围已明确则验证方案能承载它。不要求每个字段另建表格。

涉及资源或事务清理时，沿初始化、业务调用和退出等实际受影响路径，明确“主操作失败且清理也失败”与“操作成功但清理失败”的异常优先级，分别核对数据、事务状态及后续可用性。保留主异常不等于忽略所有清理错误；关闭尝试不等于资源已释放，失败结果也不等于未产生副作用。

## 按可交付行为安排实施

- 先识别风险最高的能力及外部前提。必要调查或受限原型验证结论后再固定依赖它的方案；调查结果与业务完成分别记录。
- 优先做通一条能演示、能验证的完整业务流程，再增加其他角色、异常处理和更大规模的支持。必须先建公共模块时，说明原因、如何检查接口、何时首次联调，避免各模块全部完成后才发现无法配合。
- 一个任务以可独立核对的行为或契约为边界：审查者应能单独判定它是否达标。纯准备、配置、文档步骤通常并入需要它的交付任务；确需独立交接或风险验证时才拆出。任务按依赖安排，只有接口确定且写入归属不冲突的单元才并行。
- 每项任务写明对应功能/验收、准确的现有或拟新增路径、消费/产出的接口及定义来源、必要步骤、验证命令与判定标准。步骤须能指导未参与讨论的实施者，保留可由其自行决定的函数体，不抄整份源码或写“完善相关逻辑”等空话。
- 依 [测试先行](../../../workflow/test-first.md) 为适用行为明确先RED后GREEN及必要重构步骤，沿用项目测试方法。计划写未来操作，实际结果留验证记录；例外说明原因与替代验证，命令尚不能执行时记录前置条件，不预填通过。

## 实施前自检与交接

从未参与设计的实施者视角核对，在原技术设计/实施计划末尾简述问题、修正和剩余阻塞：

1. 需求覆盖：每项功能及验收都有任务负责；全局约束明确来源；没有遗漏权限、失败恢复、兼容要求。已有成果可引用原证据，但标明是否重跑。
2. 契约一致：所有消费接口均能指向定义者；名称、类型、状态及错误语义一致；数据拥有者和共享文件写入者明确，依赖无环或有可执行的解耦方案。
3. 可执行性：任务边界、输入、交付和检查方法明确；前置条件已具备或显式阻塞；至少有整体业务集成验证的责任人和完成条件。
4. 实际使用情况：沿业务流程找出PRD没细说、但用户实际可能输入的数据或遇到的失败。需要决定业务规则的，回PRD确认；其余由相应开发任务增加检查。
5. 模板覆盖：适用内容实质覆盖，关键风险省略说明依据，无关项直接删除；没有占位符、模糊指令或重复进度，计划与task编号一致。文档很长却不能指导交付时，应收敛决策和拆分边界，而非增加说明。

首屏展示选定方案、关键代价/风险及未决影响；独立审查无阻断后按人工确认提交当前设计，确认后在批准契约内持续实施，不因单元切换重问。复杂需求按 [实施与完成门槛](../../../workflow/execution-contract.md#实施与完成门槛) 完成实施前独立审查和最终独立验收；未参与起草的开发专长查技术契约，测试专长查可验收性，由协调者安排。自检、独立审查集中记录但分别标明对象/结论/证据，不互相替代，也不替代人审。

按 [内容归属](../../../workflow/documents.md#内容归属) 逐项对应并引用：设计说明针对哪些F/AC，任务引用AC和接口定义，验证记录相应AC的实际结果。沿业务流程检查调用、状态变化、返回结果和失败处理，确保本次每项要求都有任务负责，不另建一份重复的完整对照表。发现实现与设计不同时，先判断是方案允许的细节、需要查清的问题，还是改变了范围、规则或关键方案；最后一种先说明影响，再请用户确认，不能直接改设计来迁就代码。交接只提供事项入口、当前目标/任务、相关接口、修改范围、批准依据、已验结果和待解决问题。
