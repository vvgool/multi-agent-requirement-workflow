# 复杂需求的方案与拆分

复杂需求起草技术设计、拆分实施单元或 Delta 续改前读取。先按 [人工确认](../../../workflow/execution-contract.md#人工确认) 核实需求已获批准（`req_approved`），缺少关键业务规则时退回补齐需求澄清，不靠猜测硬写架构。

## 1. 先定模块边界与契约，再拆实施单元

1. **调用链取证与复用优先**：沿真实代码入口识别可复用模块、改动点与外部 SDK/平台约束；未证实的外部能力先做只读核查。
2. **第一性原理（先删减、再下沉、后新增）**：动笔前先质疑既有假设——优先删减无需存在的历史兼容层或中间状态，将校验/同步等**机械约束下沉**给确定性代码、类型或脚本，再对影响模块边界、状态唯一写入者或交付成本的关键选择集中比较利弊（唯一合理方案直接说明依据，拒绝在腐败抽象上叠补丁）。
3. **职责正交与单写归属**：用 Mermaid 架构图（`flowchart`）标清模块职责、不负责内容与可变状态的唯一写入者；用 `sequenceDiagram` 核对主链路调用、落盘、外部交互与失败返回，消除循环依赖与多处并写。
4. **表示范围与复合失败契约**：
   - **值域与精度贯通**：涉及公共数据转换、编码或持久化时，沿 `输入 → 转换 → 存储 → 输出` 核对值域、精度与单位，防止底层默认限制无声截断已批契约。
   - **主操作与清理复合异常**：涉及事务、文件锁或资源释放时，明确“主操作失败且清理也失败”与“主操作成功但清理失败”的异常优先级及数据一致性结果；外部操作结果未知时先查询原调用，禁止自动重放。

## 2. 按可独立验证的行为拆解单元（T1..Tn）

- **端到端主干优先**：优先打通风险最高或最小可演示的完整业务主链路，再叠加扩展分支；必须先建底层公共模块时写明接口自验方式与首次联调节点。
- **单元自包含与正交写集**：每个实施单元（`T1`、`T2`…，与 `task.md` 严格同号，不在计划内重复放 `- [ ]` 复选框）写清关联 `F/AC`、精确允许写入文件、输入/产出契约、先 RED 后 GREEN 步骤（遵循 [测试先行](../../../workflow/execution-contract.md#测试先行与根因诊断)）及单元完成后的 `AC` 锚点只读回读要求。仅当接口固定且文件写集完全无交集时才允许并行派发。

## 3. 实施前自查、四项对齐审查与批准门禁

起草者按 [文档分工](../../../workflow/documents.md#按复杂度选择文档) 核对 `F/AC → 设计 D → 任务 T` 全覆盖且接口签名一致后，交由主会话安排未参与起草的独立角色执行 [架构与四项规格对齐审查](architecture-review.md)。消除阻断后在首屏展示方案与关键取舍（`pending_design_approval`），获真实用户确认（`ready_to_implement`）后进入静音连续巡航实施；实施中若新证据证伪核心契约，触发打断白名单就受影响部分重新确认，严禁私自改设计迁就错误实现。
