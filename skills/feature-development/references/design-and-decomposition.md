# 复杂需求的方案与拆分

复杂需求设计、拆分或续改前读取，并读取技术设计、实施计划模板。先检查PRD是否明确核心旅程、功能规则、可判定验收和关键未决；已有文档按内容补缺，文件存在不代表输入就绪。关键业务决策缺失时先按需求分析Skill补齐，受影响部分保持待决，独立部分可继续。

## 设计模块，再拆实施任务

产品功能回答用户能做什么，技术模块回答谁负责哪些规则和数据，实施任务回答按什么顺序交付和验证；三者通过编号关联，不要求一一对应。

1. 沿真实代码入口和调用链识别可复用能力、改动点及外部能力限制。没有核实的SDK/平台能力明确待查，先验证会影响方案的约束。
2. 对会影响模块边界、数据归属或交付成本的重要选择比较可行方案，说明推荐理由与代价；唯一合理方案说明依据，不为局部实现细节凑备选。
3. 模块分析是复杂需求的必需步骤，新增模块不是；复用现有边界时说明足够承载本次行为的依据。按业务职责、数据/状态归属和变化原因确定模块边界。每个模块明确负责和不负责的内容、拥有的数据、对外契约、依赖及验证边界。优先复用稳定约定，避免仅按页面、文件夹、技术层或角色数机械拆分。
4. 用一条核心用户旅程穿过模块，核对入口、调用、状态写入、外部副作用和结果返回。每份可变业务状态有明确拥有者；跨模块通过契约协作，关键跨模块交互用时序图。发现职责重叠、循环依赖、共享状态多头写入或接口反复穿透时先调整边界。共享文件仍单写。
5. 明确跨模块输入输出、错误语义、状态转换及版本约束。接口使用项目实际类型/签名或请求响应示例，规划中的路径和接口标为拟新增，不伪装成现有能力。异步/持久状态按风险说明超时、重复、并发与未知结果处理。

## 按可交付行为安排实施

- 先识别风险最高的能力及外部前提。必要调查或受限原型验证结论后再固定依赖它的方案；调查结果与业务完成分别记录。
- 优先尽早交付一条可演示、可验证的端到端最小业务闭环，再扩展角色、异常和规模。必须先建公共能力时，说明原因、契约检查和首个集成任务，避免所有模块各自完成后才首次联调。
- 一个任务以可独立核对的行为或契约为边界：审查者应能单独判定它是否达标。纯准备、配置、文档步骤通常并入需要它的交付任务；确需独立交接或风险验证时才拆出。任务按依赖安排，只有接口确定且写入归属不冲突的单元才并行。
- 每项任务写明对应功能/验收、准确的现有或拟新增路径、消费/产出的接口及定义来源、必要步骤、验证命令与判定标准。步骤须能指导未参与讨论的实施者，保留可由其自行决定的函数体，不抄整份源码或写“完善相关逻辑”等空话。
- 依 [测试先行](../../../workflow/test-first.md) 为适用行为明确先RED后GREEN及必要重构步骤，沿用项目测试方法。计划写未来操作，实际结果留验证记录；例外说明原因与替代验证，命令尚不能执行时记录前置条件，不预填通过。

## 实施前自检与交接

从未参与设计的实施者视角核对，在原技术设计/实施计划末尾简述问题、修正和剩余阻塞：

1. 需求覆盖：每项功能及验收都有任务负责；全局约束明确来源；没有遗漏权限、失败恢复、兼容要求。已有成果可引用原证据，但标明是否重跑。
2. 契约一致：所有消费接口均能指向定义者；名称、类型、状态及错误语义一致；数据拥有者和共享文件写入者明确，依赖无环或有可执行的解耦方案。
3. 可执行性：任务边界、输入、交付和检查方法明确；前置条件已具备或显式阻塞；至少有整体业务集成验证的责任人和完成条件。
4. 合理输入：从用户旅程查找PRD未细说但实际会遇到的输入/失败，提出合理预期；影响业务决策则回PRD澄清，其余将针对性检查归入负责代码的任务。
5. 模板覆盖：适用章节实质覆盖，删节有原因，没有占位符、模糊指令或重复进度；计划与task编号一致。文档很长却不能指导交付时，应收敛决策和拆分边界，而非增加说明。

已有授权内可继续实施；新增范围、验收分歧和具体风险遵循执行约定，不因自检、文档或任务切换再审批。复杂需求按 [实施与完成门槛](../../../workflow/execution-contract.md#实施与完成门槛) 完成实施前独立审查和最终独立验收；未参与起草的开发专长检查技术契约，测试专长检查可验收性，由协调者安排，不自行递归派发。起草者自检不代替独立检查。审查者检查PRD到方案和任务的逻辑，而非只核对标题；交接只带入口、相关文档、允许范围、已验和未决。
