# 实施前四项规格对齐与架构审查

用于复杂事项、状态性变更、架构影响型修复，或连续修复失败触发熔断后的独立只读诊断。由主会话在向用户发起 `Spec Gate` 前后台派发**未参与该稿起草或代码实现的独立角色**执行，严禁审查者直接改写起草者文档或业务源码。

## 1. 触发条件

满足任一条件时，在向用户发起 `Spec Gate`（`pending_approval`）确认前必须完成本审查闭环：
- 涉及两个以上模块、可变状态拥有者或跨边界接口契约；
- 涉及持久化、并发控制、权限转换、事务清理或跨入口一致性；
- 同一故障连续 2～3 次修复失败熔断后，证据指向模块契约或状态归属缺陷。

## 2. 强制第一步：四项规格对齐核查（防偏航核心）

审查者对照 `spec.md` 第一部分（用户目标、Non-Goals 与 `F/AC`）及第二部分（架构取舍、`Contract-First` 签名与 `T1..Tn` 单元切分）逐条比对，固定输出以下四栏诊断（附文件路径、行号或章节证据）：

1. **遗漏的 AC**：是否有任何 `F-xx / AC-xx`、关键异常、权限或恢复条件未落入具体接口契约、验证命令与实施单元 `T-xx`？
2. **擅自扩权范围**：是否塞入了用户未要求或违反 Non-Goals 的多余抽象、无关重构、额外配置项或越界文件改动？
3. **模块契约冲突**：上下游接口签名、类型、状态枚举、错误语义、共享文件单写责任人是否前后矛盾或存在循环依赖？
4. **未证实假设与边界风险**：是否将未核实的外部 SDK/宿主能力当作既定事实？[表示范围与复合失败](design-and-decomposition.md#1-先定模块边界与契约再拆实施单元)、并发重复调用、未知外部操作防重放及分层验证方案是否闭环？

## 3. 工程架构深查维度

| 维度 | 核查要点 |
| --- | --- |
| 第一性原理与防叠补丁 | 是否先删减冗余假设、将机械约束下沉至代码/脚本/结构门禁，而非在腐败抽象上叠**治标补丁**？ |
| 数据唯一拥有者 | 每份可变状态与文档是否只有一个写入责任方（如 `spec.md` 零可变状态头）？ |
| 失败与幂等恢复 | 超时、中断、重复请求与结果未知外部调用是否有明确状态边界？ |
| 单元可验证性 | 每个 `T-xx` 是否具备可独立观测的 `RED → GREEN` 或结构门禁检查，而非全部堆到最后？ |

## 4. 审查结论与闭环规则

按严重程度标注 `P1 阻断`、`P2 重要`、`P3 建议`，给出明确终态结论：
- **`可推进`**：无 `P1` 阻断（`P2` 已合入 `spec.md` 或绑定具体实施单元）；
- **`需修正复审`**：存在 `P1` 阻断，由起草者在后台修订并复审闭环后再呈交用户 `Spec Gate`；
- **`阻塞`**：发现业务目标本身存在未决分叉，交主会话向用户发起合并澄清。

> 后台独立审查通过仅代表可向用户呈交 `Spec Gate`，绝不等于跳过用户批准直接写代码，也不替代实施后的 [完成前独立对抗验收](../../acceptance-testing/references/completion-gate.md)。
