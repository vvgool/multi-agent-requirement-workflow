# 实施前四项规格对齐与架构审查

用于复杂需求、状态性变更、架构影响型修复，或连续修复失败触发熔断后的独立只读诊断。由主会话派发**未参与该设计起草或代码实现的独立角色**执行，严禁审查者直接改写起草者文档或业务源码。

## 1. 触发条件

满足任一条件时，在向用户请求设计确认（`STOP 2`）前必须执行本审查：
- 需求跨两个以上模块、可变状态拥有者或外部契约；
- 涉及持久化、并发控制、权限转换、事务清理或跨入口一致性；
- 同一故障连续 2～3 次修复失败熔断后，证据指向模块契约或状态归属缺陷。

## 2. 强制第一步：四项规格对齐核查（防偏航核心）

审查者必须先对照已批准的 `requirements.md`（或用户明确目标）与当前技术设计（含 `文件变更与单元切分` 表）逐条比对，固定输出以下四栏诊断（附具体文件路径、行号或章节证据）：

1. **遗漏的 AC**：是否有任何已批 `F-xx / AC-xx`、关键异常、权限或恢复条件未落入具体模块契约与实施单元 `T-xx`？
2. **擅自扩权范围**：是否塞入了用户未要求、甚至违反 Non-Goals 的多余抽象、无关重构、额外配置项或越界文件改动？
3. **模块契约冲突**：上下游接口签名、类型、状态枚举、错误语义、共享文件单写责任人是否前后矛盾或存在循环依赖？
4. **未证实假设与边界风险**：是否将未核实的外部 SDK/宿主能力当作既定事实？[表示范围与复合失败](design-and-decomposition.md#1-先定模块边界与契约再拆实施单元)、并发重复调用、未知外部操作防重放及可独立执行的验证方案是否闭环？

## 3. 工程架构深查维度

| 维度 | 核查要点 |
| --- | --- |
| 第一性原理与防叠补丁 | 是否质疑冗余假设、下沉机械约束并从根源收敛复杂度，而非在错误抽象上叠**治标补丁**？ |
| 数据唯一拥有者 | 每份可变状态是否只有一个写入责任方？缓存/持久化一致性是否明确？ |
| 失败与幂等恢复 | 超时、中断、重复请求与结果未知外部调用是否有明确状态边界？ |
| 单元可验证性 | 每个 `T-xx` 是否具备可独立观测的 RED/GREEN 或集成检查条件，而非全部堆到最后？ |
| 兼容与回退 | 既有配置、数据格式与调用方兼容策略及故障回退路径是否清楚？ |

## 4. 审查结论与闭环规则

按严重程度标注 `P1 阻断`（漏 AC、扩权、契约冲突、数据归属不明或无法可靠验收）、`P2 重要`（影响集成或边界稳健性，须在交付前修正）、`P3 建议`，并给出明确终态结论：
- **`可推进`**：无 `P1` 阻断（`P2` 已合入设计或绑定具体实施单元）；
- **`需修正复审`**：存在 `P1` 阻断，由原起草者修订后针对受影响项复审；
- **`阻塞`**：发现需求本身存在未决冲突，须回退澄清。

> 实施前设计审查通过不等于允许跳过用户设计确认，也不替代实施完成后的 [完成前独立对抗验收](../../acceptance-testing/references/completion-gate.md)。
