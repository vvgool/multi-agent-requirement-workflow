# 实施前四项规格对齐与架构审查

用于复杂事项、状态性变更、架构修复或盲修熔断后的独立只读诊断。由主会话在发起 `Spec Gate` 前后台派发**未参与起草或实现的独立角色**执行，禁审查者直接改写起草文档或业务源码。

## 1. 触发条件

满足任一条件时，`Spec Gate`（`pending_approval`）前必过本审查：
- 涉及两个以上模块、可变状态拥有者或跨边界契约；
- 涉及持久化、并发、权限转换、事务清理或跨入口一致性；
- 同一故障连续 2～3 次修复失败熔断后，证据指向模块契约或状态归属缺陷。

## 2. 强制第一步：四项规格对齐核查

对照 `spec.md` §1（目标、Non-Goals 与 `F/AC`）及 §2（架构取舍、`Contract-First` 签名与 `T1..Tn`）逐条比对，固定输出四栏诊断（附路径、行号或章节证据）：

1. **遗漏的 AC**：是否有 `F/AC`、关键异常、权限或恢复条件未落入具体契约签名、验证命令与 `T-xx`？
2. **擅自扩权范围**：是否塞入未要求或违背 Non-Goals 的多余抽象、无关重构、额外配置或越界写集？
3. **模块契约冲突**：接口签名、类型、状态枚举、错误语义、共享文件单写责任人是否矛盾或循环依赖？
4. **未证实假设与边界风险**：是否将未核实的 SDK/宿主能力当作事实？[表示范围与复合失败](design-and-decomposition.md#1-先定模块边界与契约再拆实施单元)、并发幂等、未知外部操作防重放及分层验证是否闭环？

## 3. 工程架构深查维度

| 维度 | 核查要点 |
| --- | --- |
| 第一性原理 | 是否先删减冗余假设并将机械约束下沉至代码/脚本门禁，而非叠**治标补丁**？ |
| 数据唯一拥有者 | 每份可变状态与文档是否仅一个写入方（`spec.md` 零状态头）？ |
| 失败与幂等 | 超时、中断、重复请求与未知外部调用是否有明确状态边界？ |
| 单元可验证性 | 每个 `T-xx` 是否具备独立可观测的 `RED → GREEN` 或结构门禁？ |

## 4. 审查结论与闭环规则

标注 `P1 阻断`、`P2 重要`、`P3 建议`，给明确终态：
- **`可推进`**：无 `P1`（`P2` 已合入 `spec.md` 或绑定实施单元）；
- **`需修正复审`**：存在 `P1`，后台修订复审闭环后再呈交 `Spec Gate`；
- **`阻塞`**：业务目标存在未决分叉，交主会话合并澄清。

> 后台审查通过仅代表可呈交 `Spec Gate`，绝不等于跳过用户批准改源码，也不替代实施后的 [完成前独立对抗验收](../../acceptance-testing/references/completion-gate.md)。
