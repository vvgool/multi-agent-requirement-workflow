# 架构审查与复盘

这是复杂需求、架构影响型 Bug 或重复失败后的按需审查方法。它补充技术设计和独立验收，不替代需求、计划或 `task.md`，也不要求为了审查新增模块。

## 何时触发

满足任一条件时，由协调者安排未参与起草的开发专长做只读审查：

- 新需求跨两个以上业务能力、数据拥有者或外部契约；
- Bug 修复会改变状态模型、公共接口、持久化格式、并发策略或失败恢复；
- 同一问题持续失败且已有证据指向跨能力契约、状态归属或架构边界问题；
- 计划中的任务可以独立完成，但首次集成才会暴露循环依赖、共享状态或边界穿透。

一次修复失败或对调用链判断不一致时，先由原角色按系统化诊断收集区分证据；仅凭失败次数不触发架构审查。持续失败而无新证据时暂停盲改，由协调者按已知风险判断所需专长，不自动升级为架构改造。局部明确小修不触发。审查范围以实际受影响的模块和核心旅程为准，不做无关的全仓架构改造。

## 检查维度

审查者沿真实入口和一条核心旅程核对以下事实，并在原技术设计或验证文档中记录结论：

| 维度 | 需要回答的问题 |
| --- | --- |
| 业务边界 | 每个模块负责什么、不负责什么？边界是否按业务职责、数据归属和变化原因划分？ |
| 数据拥有 | 每份可变状态只有一个写入者吗？读取、缓存、持久化和迁移责任是否明确？ |
| 契约方向 | 输入、输出、错误语义、版本和异步/重试约定是否由真实定义者提供？依赖是否有环？ |
| 核心旅程 | 入口、调用、状态写入、外部副作用和结果返回能否闭环？是否存在绕过契约的路径？ |
| 失败与并发 | 超时、重复、取消、并发、未知外部结果和恢复是否有明确归属与验证边界？ |
| 变化隔离 | 需求变化是否局限在相应模块？是否因页面、文件夹或角色方便而产生共享耦合？ |
| 可验证性 | 每个任务能独立观察行为和失败吗？是否有可执行的 RED/GREEN、集成和回归检查？ |
| 兼容与迁移 | 旧数据、旧调用者、配置和宿主边界是否有兼容或迁移策略？ |

审查必须给出实际证据（文件路径、行号、调用或测试结果）。不能以“文件齐全”、模型自述或静态目录存在代替架构证据。

## 结论与处理

每项发现写明触发条件、影响、严重程度和处理要求，分为：

- **阻断**：会导致需求无法实施、数据归属不明、契约不一致或无法可靠验收；修正后复审。
- **交付前修正**：不阻断当前独立单元，但会影响集成、兼容或恢复；指定任务和验证责任人。
- **后续建议**：当前范围可接受，记录依据和触发条件，不能伪装成已完成改造。

没有发现问题时也记录检查范围、证据和未检查部分。审查者不直接改写起草者文档或业务源码；原写入者合并结论，随后由协调者安排受影响范围的复验。

完成或阻塞后的轻量复盘见 [复盘与会话诊断](../../../workflow/retro.md)。
