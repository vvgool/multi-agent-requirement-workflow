# 开发与分层验证原则

## 先确定项目已有约定

读取目标路径适用的 `AGENTS.md`、架构说明、构建与测试配置，只加载与当前改动直接相关的规则；嵌套规则按作用范围应用，不将本协作框架规则误作业务项目架构。存在冲突且影响行为边界时返回待决项，不擅自大范围迁移无关模块。

## 缺少约定时采用 Clean Architecture 原则

- 将业务核心规则与 UI、网络、数据库、宿主 SDK 等外部细节解耦；外层依赖内层，核心逻辑通过显式输入/输出保持可独立测试。
- 按实际复杂度适度分层：局部功能只需分离纯逻辑函数与外部 I/O 边界，不为简单修改套用冗余仓储层或过度依赖注入。

## Contract-First 与 SDD/TDD 分层验证

修改严格收敛于批准规格范围，禁止顺带重构无关代码，并按变更介质选择最优验证方法：

1. **业务与脚本代码（`Contract-First` + 行为级 TDD）**：先固定跨模块接口签名、数据结构与异常语义（`Contract-First`），针对外部可观察行为编写失败测试核实真实 `RED`，再做最小实现达 `GREEN` 并必要清理，不为凑覆盖率堆砌脆弱实现细节断言。
2. **文档、规则与配置契约（`SDD` + 纯结构不变量门禁）**：以规格驱动（`SDD`）收敛概念边界与不变量；静态测试仅校验 Schema、真实文件与 GFM `#标题锚点` 可达性、格式红线及体积上限，严禁编写跨文件自然语言长句快照测试锁死正常演进。
