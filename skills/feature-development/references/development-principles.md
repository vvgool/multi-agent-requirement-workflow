# 开发原则

## 先确定项目已有约定

读取目标路径适用的 AGENTS.md、宿主项目说明、架构/ADR、贡献约定，以及实际使用的构建、格式化、测试和 CI 配置。只读取与改动相关的内容；嵌套规则按作用范围应用，不能将框架自身规则当作业务项目架构。

以当前有效的用户要求及适用项目规则为依据，结合实际代码确认现状。规则存在冲突或实现与约定不同，先查明原因；无法确定且影响实现时返回具体待决策问题，不自行大范围迁移架构。

在所选开发文档的规则依据位置记录已找到的规则和采用的约定。查找后未发现架构约定，明确记录，再采用下述默认原则。代码中的稳定惯例仍需尊重，避免无关重构。

## 缺少约定时采用 Clean Architecture 原则

- 将业务规则和用例与 UI、网络、数据库、宿主 SDK 等外部细节分离；外层依赖业务核心，业务核心不直接绑定外部框架。
- 业务判断集中在清晰职责的函数或模块中，通过显式输入/输出表达行为；外部读写放在适当边界，便于独立验证。
- 外部能力需要替换或影响业务测试时，通过参数、函数或合适的接口传入，由外层组装；按实际语言和技术栈选择形式。
- 按实际复杂度落地：小需求可只分离纯业务函数和调用方；复杂需求再明确业务、用例和外部适配职责。无需为每项修改创建全套层级、仓储接口或依赖注入框架。

## 实现与验证

修改集中于批准需求所需范围，复用项目已有能力；只为真实变化和测试需要增加抽象。命名、错误处理、日志、依赖和验证命令遵循项目约定，禁止借需求顺带重构无关代码。

依据行为与风险选择必要检查，覆盖当前变更、异常及受影响路径；不为凑数量生成重复测试。业务验证和架构约束都要核对，发现不符合约定的依赖或耦合时在当前范围内修正，超出范围则说明问题和下一步。
