# 开发工作流

在已批准范围内完成实现与完整功能自验。文档按复杂度裁剪，执行方式按模块选择；两者分别判断。

接单及交付前遵循 [阶段执行契约](../../workflow/execution-contract.md)，统一核对身份、授权、结果位置和过期任务。正式文稿及根状态由协调层维护；内部身份及证据索引留执行记录。

## 接单与开发原则

完成执行契约核对后，业务决策缺失返回 needs_input，执行条件不足返回 blocked；范围变化交协调层重新确认。

先读 [开发原则](references/development-principles.md)：遵循适用项目规则和已有架构约定；缺少约定时按 Clean Architecture 的职责划分和依赖方向做最小设计。规则来源和技术选择记入下述文档，不另建原则报告。

## 选择文档档位

读取相关入口、调用方、批准需求及适用缺陷报告，核实已有实现和可用检查命令。区分既有失败与本次变更：只运行能帮助判断影响的现有检查，已有可靠同基线记录可引用；关键路径无法验证时说明限制，不能把全项目无关检查都设为门禁。按实际影响选择：

| 档位 | 适用条件 | 读取真实模板并生成到 task.output_dir |
| --- | --- | --- |
| 简版 | 范围清楚、局部低风险，依赖和验证路径简单 | [开发记录](assets/templates/development.md) → development.md |
| 完整版 | 跨多个业务模块/系统、关键接口或数据迁移、高风险行为，或技术不确定性需要展开 | [方案](assets/templates/technical-plan.md)、[计划](assets/templates/implementation-plan.md)、[自验](assets/templates/verification.md) → 对应同名文件 |

默认按实际影响选档，不额外填写档位理由；升级为完整版或选择不明显时，才在已有记录简述原因。不按行数或工期机械分类。

首次代码修改前完成可实施方案与任务；完整版自验文件在实际验证后生成。当前修订开发/测试内、同一批准范围中局部低风险且原方案仍适用的缺陷修复，使用简版：本run development.md 引用原方案，修改前简述缺陷及关联AC、拟改位置和验证方法，交付时补实际改动、验证结果及限制；不重复原模块拆分、任务表或档位说明。旧文稿和结果保持原样，本run仍绑定当前任务、审批及新代码基线；影响扩大或原方案失效时补充适用设计。

先读取模板再填实际内容，替换占位符并删除不适用的条件段；普通简版用任务复选列表（上述小修复可省略任务表），完整版按依赖顺序分模块列任务复选项，稳定编号关联验收及证据；只生成适用档位，不额外生成空方案、改动清单或检查点文件。已有文稿、旧 run 和证据保留，按索引读取，不为统一格式批量重建。简版升级时引用已有内容、补足缺项即可。

完整版按技术方案模板的条件章节提供架构/流程图及模块或接口实现细节，核对图、方案与计划一致。

## 规划、执行与恢复

修改代码前明确实现方式、接口/数据流、影响及检查方法。大需求先按可交付能力拆独立可验证模块，明确输入输出、解决循环依赖并排序，再拆有目标、前置条件和完成标准的小任务；覆盖全部验收。简版将单模块和少量任务合并在一页。模块模式按复杂度、依赖、验证成本和恢复需要分别选择，必要取舍并入方案。

规划完成后核对：每个验收项有实现和验证归属，跨模块接口一致，依赖可执行。模块按可交付能力划分，任务以可独立检查的行为为界；单独建目录、接线或写文档仅在确能独立验证交付时单列，否则合并到使用它的任务。

规划可实施后按 [方案通知](../../workflow/execution-contract.md#开发中方案通知) 在同run通知协调并自主继续；后续文稿更新、写入保护及旧任务兼容统一按该契约处理。

- 任务进度只维护在本次 implementation-plan.md 的复选列表；简版使用 development.md 的任务节，小修复使用其改动/验证条目。通过对应检查后勾选完成，阻塞、需重验及必要下一步写在原条目旁。连续完成的小任务可合并一次保存，暂停、交接或上下文可能丢失前及时更新。
- run 不维护第二套任务状态、进度日志或恢复表；长任务与中断按 [恢复指引](references/long-execution.md) 从计划、实际代码和验证证据恢复。实际检查证据须在丢失前保存，关键失败与重验分别保留。

收到失败报告或遇到测试/运行异常时，先读取报告并复现，沿实际调用链定位原因，选择最小相关检查验证判断后再修改。修复行为缺陷时，优先用能区分错误与正确行为的回归检查验证失败再修复；无法自动化或环境受限时记录实际依据，不编造红绿结果。修复后重验旧缺陷及受影响任务/下游；同一尝试没有新证据或错误反复出现时停止盲改，汇总已试方法及所缺条件，按需返回 needs_input/blocked。

计划是唯一任务进度来源；内部证据按执行契约保存，共享自验文稿保留可读检查事实。使用当前宿主工具即可，不依赖个人安装的辅助 Skill 或后台服务。

## 自验与交接

所有批准需求都需完整功能自验，包含适用的集成、异常和回归。简版写在 development.md，完整版写在 verification.md；改动及限制并入该交付记录。未执行不预填通过，局部通过不代替整体自验。

交付前审视最终差异与真实调用路径：需求有无遗漏/擅自扩展、接口及错误行为是否符合约束、改动是否破坏相关既有行为。发现遗漏先修正并重验受影响范围，不为每次改动额外创建审查报告或强制增加 Agent。

所有检查完成后，读取 [代码基线契约](../../workflow/code-baseline.md) 记录已验证代码及未提交改动；按执行契约“最终交接与摘要收敛”和 [结果模板](../../templates/role-result.yaml) 完成文稿与 result.yaml。artifacts：简版使用 development_record，完整版使用 technical_plan、implementation_plan、verification。

ready 要求全部必需任务/模块检查及整体自验通过、无影响交付的未解决项、基线对应已验证代码。否则继续修复或如实返回 needs_input/blocked。向协调层返回实际产物和结果路径；交接按实际内容核对，不要求简版提供完整版文件名。
