# 开发工作流

在已批准范围内完成实现与完整功能自验。文档按复杂度裁剪，执行方式按模块选择；两者分别判断。

接单及交付前遵循 [阶段执行契约](../../workflow/execution-contract.md)，统一核对身份、授权、结果位置和过期任务。正式文稿及根状态由协调层维护；文稿按 [共享成果规则](../../workflow/output-layout.md#共享成果与本机现场) 面向人和AI独立可读，内部身份及证据索引留执行记录。

执行检查前按该契约的 [缓存与证据](../../workflow/execution-contract.md#缓存与证据) 核对实际缓存位置和授权；自验记录合并命令/范围、结果、基线及环境事实，同一检查多个任务/AC共用一个编号与必要输出。复用先核实原result与适用条件，并注明本轮未重跑；收敛现场交协调在确认调用结束后处理。

## 接单与开发原则

完成执行契约核对后，业务决策缺失返回 needs_input，执行条件不足返回 blocked；范围变化交协调层重新确认。

先读 [开发原则](references/development-principles.md)：遵循适用项目规则和已有架构约定；缺少约定时按 Clean Architecture 的职责划分和依赖方向做最小设计。规则来源和技术选择记入下述文档，不另建原则报告。

## 选择文档档位

读取相关入口、调用方、批准需求及适用缺陷报告，核实已有实现和可用检查命令。区分既有失败与本次变更：只运行能帮助判断影响的现有检查，已有可靠同基线记录可引用；关键路径无法验证时说明限制，不能把全项目无关检查都设为门禁。按实际影响选择：

| 档位 | 适用条件 | 读取真实模板并生成到 task.output_dir |
| --- | --- | --- |
| 简版 | 范围清楚、局部低风险，依赖和验证路径简单 | [开发记录](assets/templates/development.md) → development.md |
| 完整版 | 跨多个业务模块/系统、关键接口或数据迁移、高风险行为，或技术不确定性需要展开 | [方案](assets/templates/technical-plan.md)、[计划](assets/templates/implementation-plan.md)、[自验](assets/templates/verification.md) → 对应同名文件 |

档位、理由及模块执行模式记录在本run执行记录，不重复写入正式文稿；不按行数或工期机械分类。小需求可以只有一个模块、少量可验证任务。每模块仍按复杂度、依赖及恢复需要选择普通/长任务，完整文档不代表所有模块都要长任务。

首次代码修改前先完成适用方案与任务，且达到可实施程度；完整版自验文件在实际验证后生成，不预建空稿。存在需要展开的架构/流程或关键接口复杂性时选完整版，简版不能绕过必要设计。

先读取模板再填实际内容，替换占位符并删除不适用的条件段；简版用任务复选列表，完整版用模块顺序表及逐项任务条目，稳定编号关联验收及证据；只生成适用档位，不额外生成空方案、改动清单或检查点文件。已有文稿、旧 run 和证据保留，按索引读取，不为统一格式批量重建。简版升级时引用已有内容、补足缺项即可。

完整版技术方案按模板的条件章节输出：涉及框架或架构须有架构图，涉及业务或执行流程须有流程图，两者同时涉及则均提供；按模块或接口展开具体实现，并核对图、实现方案和执行计划的对应关系。图示及实现细节的填写要求以技术方案模板为准。

## 规划、执行与恢复

修改代码前明确实现方式、接口/数据流、影响及检查方法。大需求先按可交付能力拆独立可验证模块，明确输入输出、解决循环依赖并排序，再拆有目标、前置条件和完成标准的小任务；覆盖全部验收。简版将单模块和少量任务合并在一页。模块模式按复杂度、依赖、验证成本和恢复需要分别选择，理由留执行记录。

规划完成后核对：每个验收项有实现和验证归属，跨模块接口一致，依赖可执行。模块按可交付能力划分，任务以可独立检查的行为为界；单独建目录、接线或写文档仅在确能独立验证交付时单列，否则合并到使用它的任务。

规划可实施后，按 [开发中方案通知](../../workflow/execution-contract.md#开发中方案通知) 原子提交完整文稿版本清单并在同 run 通知协调；正常通知后立即自主继续，不等展示回执或常规技术批准。候选文稿及清单更新须先核对已知摘要、归属和pending意图，保留用户编辑，恢复时只补可证实的同版本操作；具体格式与单写者/双读规则以该契约为准。调整时更新受影响图、模块、任务与检查并记录原因及AC影响，提交新版本通知；范围/验收变化交修订，写入安全不足blocked。已有方案在needs_input/blocked时同样通知真实状态；full仅部分有效稿时按契约用plan_partial，列missing_artifacts及问题/解除条件，不冒称完整ready；无稿明确未产出，不建空文件。

- 普通模块按依赖及任务顺序实施，任务和模块检查通过后更新进度，再推进相关下游；调整计划保留原因。
- 长任务或恢复按 [恢复指引](references/long-execution.md) 实施，恢复信息留本run执行记录。

收到失败报告或遇到测试/运行异常时，先读取报告并复现，沿实际调用链定位原因，选择最小相关检查验证判断后再修改。修复行为缺陷时，优先用能区分错误与正确行为的回归检查验证失败再修复；无法自动化或环境受限时记录实际依据，不编造红绿结果。修复后重验旧缺陷及受影响任务/下游；同一尝试没有新证据或错误反复出现时停止盲改，汇总已试方法及所缺条件，按需返回 needs_input/blocked。

计划只维护进度及共享自验文稿中的检查结论引用；内部证据路径及精确基线引用留本run执行记录，验证文稿维护可读检查事实。同一真实检查满足多个条件时执行一次并引用，不重复抄写；真实集成要求仍须满足。使用当前宿主工具即可，不依赖个人安装的辅助 Skill 或后台服务。

## 自验与交接

所有批准需求都需完整功能自验，包含适用的集成、异常和回归。简版写在 development.md，完整版写在 verification.md；改动及限制并入该交付记录。未执行不预填通过，局部通过不代替整体自验。

交付前审视最终差异与真实调用路径：需求有无遗漏/擅自扩展、接口及错误行为是否符合约束、改动是否破坏相关既有行为。发现遗漏先修正并重验受影响范围，不为每次改动额外创建审查报告或强制增加 Agent。

所有检查完成后按执行契约“最终交接与摘要收敛”生成真实结果、提交最终文稿及末次清单，核对结果中文稿摘要及通知指针一致后再交接。文稿不链接内部结果，关联由结果单向维护。

按 [结果模板](../../templates/role-result.yaml) 在指定结果位置生成 result.yaml。身份、阶段结果及最终代码基线统一以它为交接来源，文档引用即可；生成最终基线前读取 [代码基线契约](../../workflow/code-baseline.md)，按统一文件清单记录实际已验证代码及未提交改动。artifacts 每项含 kind/path，路径相对当前输出目录：简版可用 kind: development_record，完整版用 technical_plan、implementation_plan、verification。

ready 要求全部必需任务/模块检查及整体自验通过、无影响交付的未解决项、基线对应已验证代码。否则继续修复或如实返回 needs_input/blocked。向协调层返回实际产物和结果路径；交接按实际内容核对，不要求简版提供完整版文件名。
