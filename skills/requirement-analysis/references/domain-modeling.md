# 需求阶段的轻量领域建模

当多角色权限、持久状态、并发幂等或失败恢复共同决定业务行为时按需读取，服务于 `spec.md`（§1）与 `AC` 判定，不为局部小修单独建领域文档。

## 最小领域快照（直接并入 `spec.md` §1）

| 维度 | 回答的核心问题 | 最小表达 |
| --- | --- | --- |
| 角色与边界 | 谁发起动作、谁可见结果、与哪个外部系统交互？ | 角色与信任边界列表 |
| 核心概念 | 哪些业务名词不可混用？唯一标识与生命周期是什么？ | 紧凑术语表（含禁用混称） |
| 状态与不变量 | 哪些状态转换合法？什么条件在任何时刻都必须成立？ | `stateDiagram-v2` + 不变量清单 |
| 动作与可观察结果 | 成功、拒绝、重复提交与外部结果未知时分别呈现什么？ | 动作—结果对照 |

## 建模与事实分类规则

1. **忠于业务原词**：提取用户原话与现有项目术语，对易混淆概念写一句可判定定义及反例；底层表名或类名留给 `spec.md` §2 架构契约。
2. **不变量绑定 AC**：每条业务不变量（如“同一订单超时释放库存至多生效一次”）必须直接体现在对应的 `F-xx` 与 `AC-xx` 中。
3. **事实、建议与待决分离**：
   - **已核实事实**（标注用户原话或代码路径依据）：可直接写入规格，整体按 [人工确认](../../../workflow/execution-contract.md#人工确认) 经 `Spec Gate` 取得批准；
   - **Agent 可逆建议**：注明推荐方案与回退方式，不阻塞后台审查；
   - **必答业务未决**：一次性合并列入 `task.md` 的 `## 本次请确认`，未获决定前严禁以默认值冒充用户批准。
