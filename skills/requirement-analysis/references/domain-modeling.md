# 需求阶段的轻量领域建模

复杂需求起草或续改时读取。当多个角色、持久状态、权限、并发、恢复或跨模块契约共同影响行为时，先把业务语言和规则稳定下来，再比较产品方案。这里的模型服务于 PRD 与验收，不替代技术设计，也不要求为每个小修创建 `CONTEXT.md`。

## 建模目标

用项目已经使用的词描述“谁对什么做什么，以及状态如何变化”。只记录会改变范围、模块边界、验收或风险的内容；可逆的实现细节留给技术设计。每个词都要能追溯到用户描述、现有实现、外部约束或明确标记为待决假设。

按需要形成以下最小快照，直接写入 `requirements.md` 的“领域模型与业务语言”小节；若项目已有领域词汇文档则引用它，不复制第二份：

| 项目 | 要回答的问题 | 最小产物 |
| --- | --- | --- |
| 角色/边界 | 哪个角色或外部系统发起动作？谁能看到结果？ | 角色与信任边界 |
| 核心概念 | 业务中哪些名词不可互换？标识和生命周期是什么？ | 术语表（同义词、禁用混称） |
| 状态/不变量 | 哪些状态转换合法？什么条件始终必须成立？ | 状态表或状态图、规则清单 |
| 动作/结果 | 谁发起命令？成功、拒绝、重复和未知结果如何观察？ | 动作—结果表 |
| 业务责任 | 谁负责这项业务事实、谁有权改变它？ | 概念到业务责任主体映射；已知实现另标为现状 |

## 从对话到模型

1. 先抽取用户原话中的名词、角色、动作、状态和数量约束，保留原词并标出同义词候选；不要先用代码类型替换业务概念。
2. 对每个核心名词写一句可判定定义，并列出一个反例（何时它不是另一个相似概念）。发现同一个词在不同旅程含义不同，就拆成限定词不同的术语或列为待决。
3. 沿核心旅程标出状态转换、重复请求、并发冲突、撤销/恢复和外部副作用。跨角色交接必须说明交接前后的可见结果。
4. 把不变量连接到功能和验收编号，例如“同一资源同一时间只能有一个有效占用”必须在 F-xx 与 AC-xx 中出现；只有实现者能决定的存储/类名不写成业务规则。
5. 将概念、业务责任和已知实现交给技术设计。具体模块、存储写入边界和接口由技术设计确定或核对；未定的实现分配不阻塞业务规则已清楚的PRD。技术设计可有依据地复用现有边界。

## 澄清与决策账

采用三栏决策表，避免把模型推断伪装成用户确认：

| 状态 | 写法 | 推进规则 |
| --- | --- | --- |
| 已确定 | 结论 + 来源（用户/现有行为/约束） | 可直接进入设计与验收 |
| Agent 建议或可逆决定 | 建议 + 影响 + 回退方式 | 不阻塞独立范围；实施时显式记录采用结果 |
| 必须澄清/未验证假设 | 问题 + 会改变的行为/验收 + 受影响范围 | 关键规则未决时冻结受影响实施；先推进无关部分 |

一次只提出会改变模型或验收的最少问题，并先检查代码、现有文档和平台约束。已回答的问题不重复问；不要为了“完整模型”询问不影响交付的术语偏好。用户未及时决定时，保留待决状态，不以默认值冒充确认。

## 交付前检查

- 每个 PRD 功能和验收都能指向至少一个角色、概念或状态转换。
- 关键名词在需求、设计、计划和验收中的含义一致；同义词已经映射或明确禁止混用。
- 状态、不变量、权限和失败/恢复规则有可观察结果；模型没有只描述数据库字段而遗漏业务行为。
- 每项业务事实的责任主体和修改权限清楚；已有实现与业务预期的冲突被标明。技术模块、存储写入和跨模块契约由技术设计承接，不将实现分配冒充业务确认。
- 待决项说明影响和可独立推进范围；未验证的外部能力没有写成已确认事实。

模型快照只在复杂需求或原事项确实发生语义变化时更新。普通文档修订、角色切换和小修不触发重新建模或重复审批。
