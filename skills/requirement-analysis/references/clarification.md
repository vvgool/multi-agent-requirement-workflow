# 复杂需求的产品设计

复杂需求起草或续改时读取。目标是让未参与对话的人理解要解决什么问题，并能据此做技术设计和验收。requirements.md 承载 PRD，已有项目 PRD 按内容覆盖后引用，不另写一份。

## 从问题到方案

1. 先读用户描述、现有产品和相关实际实现，用一条真实场景回述目标、现有行为及约束，并注明代码/配置/测试等证据。区分用户明确要求、Agent建议、未验证假设；用户未提及的内容不能自动算作排除项，建议也不能写成已确认结论。
2. 需要时按 [领域建模方法](domain-modeling.md) 梳理角色、业务概念、状态、必须始终成立的规则（不变量），以及谁有权决定或修改业务规则。沿用用户的业务用语；同一个词有不同含义且会影响流程或验收时，先列出来确认。模块划分、数据存储和修改由技术设计说明，局部小修不另建领域文档。
3. 按用户角色梳理业务流程：谁来操作、需要什么条件、经过哪些步骤、得到什么结果，失败后怎么办、需要谁接手。用流程图表示步骤和分支，文字补规则和例外；有界面时说明页面状态，必要时用线框或原型核实；无界面时说明谁调用、返回什么。检查对现有用户的影响，不用技术调用链代替业务流程。
4. 主动找出描述中的遗漏和冲突。先从项目查答案，再按影响提出最关键的问题；问题说明会改变哪项产品行为或领域规则。日常可逆实现细节由Agent决定并说明；影响范围、业务规则、验收或风险的未决不能用默认值冒充用户决定。多个问题按依赖分批，已有答案不重复询问。
5. 确有产品路径或关键技术取舍时，给出两到三个可行方案的收益、代价及推荐理由；只有一个合理方案时说明依据。产品取舍留在PRD，技术取舍由技术设计维护；不要为了凑数比较虚假方案。不可确定的可行性先做受限调查，原型须在已有授权范围内且标明用途和限制。
6. 按PRD模板形成完整产品方案：给功能稳定编号（如F-01），把领域规则、不变量和状态转换连接到核心流程、业务规则、异常、权限与验收。非功能要求只列影响使用与交付的指标及环境；未知指标标明待决，不杜撰性能、规模、合规或平台承诺。

## 决策边界

在原PRD区分已确定事项及依据、实施者可自行决定的可逆细节、必须澄清的业务决策，并在领域模型中保持术语、状态与不变量的来源。建议未被采纳或假设未被验证时如实标记，不能擅自升为确定要求。原需求已明确时只补受影响缺口，不重新设计无关功能。

## 实施前检查

起草者从未参与对话的实施者视角逐项检查，在PRD末尾简述发现、修正和剩余阻塞，不另建审查文档：

- 每个目标是否有相应功能和业务流程，用户是否能得到预期结果？失败、重复操作和各角色权限是否说清？
- 复杂规则是否有足够的领域模型快照：核心术语可区分，状态转换和不变量能映射到功能/验收，业务责任和修改权限清楚？省略可能影响行为的内容时是否有依据，而非为无关项凑说明？
- 每项功能是否有稳定编号和可判定的验收，是否存在互相冲突的规则、缺失的状态或未经确认的业务假设？验收应覆盖正常、关键异常和边界行为。
- 适用的模板内容是否实质覆盖？沿用项目格式，关键风险省略有依据，无关章节删除；空标题、占位符和“按需处理”等模糊表述不算覆盖。
- 实施者能否在不猜业务决策的情况下继续设计？不能则列明具体问题、影响及可先推进的独立范围。影响关键流程的未决解决前，不实施受其影响的部分。

在开头说明本次做什么、建议怎么做、哪些问题需要确认及影响，按 [人工确认](../../../workflow/execution-contract.md#人工确认) 展示需求，用户确认后才进入正式设计。起草者自查和适用的独立检查在原文末尾分别记录，不重复方案比较。已批准范围内的普通修订和角色切换不重审。复杂需求按 [实施与完成门槛](../../../workflow/execution-contract.md#实施与完成门槛) 安排实施前独立审查和最终独立验收；检查业务流程、功能/验收编号（F/AC）与方案是否一致，而不只看排版。专业审查由协调者安排，起草者不自行继续派角色。交接时提供PRD和待确认问题，业务规则只在原PRD维护，task简述并链接。
