# 复杂需求的产品设计

复杂需求起草或续改时读取。目标是让未参与对话的人理解要解决什么问题，并能据此做技术设计和验收。requirements.md 承载 PRD，已有项目 PRD 按内容覆盖后引用，不另写一份。

## 从问题到方案

1. 先读用户描述、现有产品和相关实际实现，说明现状、受影响用户、问题及证据。区分用户明确要求、Agent建议、未验证假设；用户未提及的内容不能自动算作排除项，建议也不能写成已确认结论。
2. 需要时按 [领域建模方法](domain-modeling.md) 抽取角色、核心概念、状态、不变量和业务责任主体。先保留用户业务语言，再把会影响旅程、验收或边界的术语冲突列入决策表；具体技术模块和存储写入归属交由技术设计，不为小修创建额外领域文档。
3. 按用户角色走完核心旅程：入口与前置条件、关键操作、系统反馈、成功结果，以及失败后的退出或恢复。涉及界面时说明页面/交互状态，必要时用线框或原型核实；没有界面的能力则说明调用方及可观察结果。检查角色之间的交接和存量用户行为。
4. 主动找出描述中的遗漏和冲突。先从项目查答案，再按影响提出最关键的问题；问题说明会改变哪项产品行为或领域规则。日常可逆实现细节由Agent决定并说明；影响范围、业务规则、验收或风险的未决不能用默认值冒充用户决定。多个问题按依赖分批，已有答案不重复询问。
5. 确有产品路径或关键技术取舍时，给出两到三个可行方案的收益、代价及推荐理由；只有一个合理方案时说明依据。产品取舍留在PRD，技术取舍由技术设计维护；不要为了凑数比较虚假方案。不可确定的可行性先做受限调查，原型须在已有授权范围内且标明用途和限制。
6. 按PRD模板形成完整产品方案：给功能稳定编号（如F-01），把领域规则、不变量和状态转换连接到核心流程、业务规则、异常、权限与验收。非功能要求只列影响使用与交付的指标及环境；未知指标标明待决，不杜撰性能、规模、合规或平台承诺。

## 决策边界

在原PRD区分已确定事项及依据、实施者可自行决定的可逆细节、必须澄清的业务决策，并在领域模型中保持术语、状态与不变量的来源。建议未被采纳或假设未被验证时如实标记，不能擅自升为确定要求。原需求已明确时只补受影响缺口，不重新设计无关功能。

## 实施前检查

起草者从未参与对话的实施者视角逐项检查，在PRD末尾简述发现、修正和剩余阻塞，不另建审查文档：

- 每个目标是否有用户旅程和功能承接，是否能走到用户可观察的结果？关键失败、重复操作及角色权限是否明确？
- 复杂规则是否有足够的领域模型快照：核心术语可区分，状态转换和不变量能映射到功能/验收，业务责任和修改权限清楚？若不适用，是否说明原因？
- 每项功能是否有稳定编号和可判定的验收，是否存在互相冲突的规则、缺失的状态或未经确认的业务假设？验收应覆盖正常、关键异常和边界行为。
- 适用的模板内容是否实质覆盖？保留已有文档格式，删去不适用章节时简述原因；空标题、占位符和“按需处理”等模糊表述不算覆盖。
- 实施者能否在不猜业务决策的情况下继续设计？不能则列明具体问题、影响及可先推进的独立范围。影响关键流程的未决解决前，不实施受其影响的部分。

把关键方案、Agent作出的重要判断和仍需用户决定的问题简短呈现给用户。确认遵循项目已有授权和风险规则；已经确认的范围、普通文档修订和角色切换不重复审批。复杂需求按 [实施与完成门槛](../../../workflow/execution-contract.md#实施与完成门槛) 安排实施前独立审查和最终独立验收；审查核对需求与方案，而非只看排版。由协调者安排专业审查，产品起草者不自行递归委派。交接传PRD及未决项，业务决策继续写回原PRD，task.md摘要并链接。
