# 深入澄清

仅在多决策依赖、复杂/高风险或用户要求深入质询时读取。决策关系按当前理解推演即可，已解决结论和答复沿用 input.md/历史结果；不额外创建决策树、问卷或澄清报告。

## 沿决策依赖提问

先识别会改变目标、参与者、范围或关键行为的决策，再找依赖它们的边界和异常规则。每轮只问前置已解决的部分，答复后重新判断哪些问题仍有意义；被前一选择排除的分支不再追问。可由代码/规则核实的事实先核实，待查事实不能作为未经确认的提问前提。

例如“每天发放奖励”：先核实项目是否已有账户与时间规则，再确定仍未明确的领取主体或奖励条件；只有明确主体后，才讨论与其相关的重复领取、跨端或游客转正。不要同时让用户回答依赖不同主体假设的问题。

## 问题质量

每题聚焦一个会改变验收的决策，给出可理解的选择、推荐及理由；可使用反例或失败场景暴露冲突。既有规则足够明确时直接引用，不把它重新变成选项。推荐应服从已知目标及项目约束，不能引入未要求的功能。

关键高风险维度按实际相关性展开：不可逆数据变更的业务预期、权限边界、资金/计数一致性、失败后可恢复行为。具体技术机制和架构方案交开发；必要可行性事实先只读调查，无法核实时说明限制。

## 收敛与停滞

答复部分明确时保留有效已决结论，只追问剩余或冲突项。输出问题时按 [交接契约](../../../workflow/handoff.md#澄清记录与再次派发) 说明依赖与失效条件；协调层可转达仍有效问题，只有需重新分析或答齐整理文稿才再次调用产品。再次接单先核对触发原因和全部累计输入，因上游变化失效的问题先更新，不机械重问原题。用户回答“按建议”时须能对应本轮实际展示且仍有效的具体建议，不将其扩展为其他业务授权或正式需求审批。

多轮仍无新信息或目标发生根本变化时，集中说明当前冲突、已知取舍及最小待决策事项，返回 needs_input；能力/资料不足则 blocked。不能重复同样问题消耗轮次，也不能为结束流程默填规则。

结束条件沿用 Skill：已能完整描述范围内行为并逐项验收，关键未知项已清除。内部实现上的可替换选择不影响澄清结束。确认对象最终仍为协调层展示的本版需求文稿。
