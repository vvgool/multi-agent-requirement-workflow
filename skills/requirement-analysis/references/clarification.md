# 复杂事项的产品规格设计

复杂事项起草 `spec.md` 第一部分或 Delta 续改时读取。目标是让未参与对话的实施者与独立验收者仅凭 `spec.md` 即可无歧义完成契约实现与对抗验收（已有项目文档时就地补缺引用，不重复建第二份）。

## 从问题到可判定规格

1. **穿透 XY 问题与代码取证**：先读用户描述及直接相关的代码、配置与测试，剥离口述**表面解法**（X）追问背后的**根本矛盾**（Y）与硬约束；说明现状痛点、预期变化与非目标（Non-Goals），严禁把未证假设伪装成事实。
2. **业务概念与状态边界**：涉及多角色、持久状态或并发幂等时，按 [轻量领域建模](domain-modeling.md) 明确核心术语、合法状态转换与必须始终成立的不变量（Invariants），标清谁有权改变业务状态。
3. **业务流程与异常兜底**：用 Mermaid `flowchart` 表达触发条件、分支与失败/重复提交/权限不足时的可观察结果。
4. **一次性合并澄清**：先查代码排除伪问题；常规可逆细节给推荐默认值，**所有真正改变范围、行为或验收的未决分叉一次性合并提交**（列入 `task.md` 的 `## 本次请确认`），说明每题影响哪条 `F/AC`，禁止拆轮挤牙膏追问。
5. **稳定编号闭环**：为功能（`F-01`…）和验收标准（`AC-01`…）赋予稳定编号，确保每条不变量、关键异常与高危边界均映射到具体可判定的 `AC`。

## 起草内省与门禁交接

展示或送审前以未参与讨论者视角内省（不在文档留自查填空栏）：目标与非目标是否直指根本矛盾？每项 `F-xx` 的正常、异常与边界 `AC-xx` 是否可判定且零空洞占位符？

注意 `spec.md` 不放可变状态头：阶段状态（`pending_approval` 或超大模糊项目的 `pending_req_approval`）与批准记录唯一由 `task.md` 维护，遵循 [人工确认](../../../workflow/execution-contract.md#人工确认) 与 [实施与完成门槛](../../../workflow/execution-contract.md#实施与完成门槛)。
