# 复杂需求的产品设计

复杂需求起草或 Delta 续改时读取。目标是让未参与对话的实施者与独立验收者仅凭 `requirements.md` 即可无歧义完成设计与验收（项目已有 PRD 时就地补缺引用，不重复建第二份）。

## 从问题到可验收方案

1. **穿透 XY 问题与代码取证**：先读用户描述及直接相关的现有实现、配置与测试，剥离用户口述的**表面解法**（X）追问背后的**根本矛盾**（Y）与不可妥协硬约束（若表面解法治标不治本，须基于事实指出更本质方案）；用真实场景说明现状痛点、预期变化与非目标（Non-Goals），严禁把未证假设伪装成事实。
2. **业务概念与状态边界**：涉及多角色、持久状态或并发约束时，按 [轻量领域建模](domain-modeling.md) 明确核心术语、合法状态转换与必须始终成立的不变量（Invariants），并标清谁有权改变业务状态。
3. **业务流程与异常接手**：用 Mermaid `flowchart` 表达谁在什么条件下操作、经历哪些分支、产生什么可观察结果，以及失败、重复提交或权限不足时的处理结果，不用底层代码调用栈代替业务流程。
4. **一次性合并澄清**：主动排查描述遗漏与规则冲突。先查代码排除伪问题；日常可逆工程细节给出推荐做法并标明，**所有真正改变产品行为、范围或验收的未决问题一次性合并提出**，说明每题影响哪条 `F/AC`，禁止多轮挤牙膏式追问。
5. **真实产品取舍**：确有多条可行产品路径时，集中比较 2～3 个真实选项的收益、代价与推荐依据；技术实现层面的模块选型留给技术设计。
6. **稳定编号闭环**：为功能（`F-01`…）和验收标准（`AC-01`…）赋予稳定编号，确保每条不变量、关键异常与高危边界都能映射到具体可判定的 `AC`。

## 实施前自查与门禁交接

起草者在展示前以未参与讨论的实施者视角逐项自查（自查在生成过程中完成，不在文档留自查填空栏）：
- 是否已剥离伪需求，让目标与非目标直指根本矛盾？失败、重复操作与权限是否无歧义？
- 每项 `F-xx` 是否都有覆盖正常、异常与关键边界的可判定 `AC-xx`，且无空洞占位符？
- 是否仍存在需要实施者“猜业务规则”的隐含假设？

首屏明确标注 `阶段状态: pending_req_approval`、核心结论与 `## 本次请确认`（不设条数上限，多项按主题分组，每项带推荐与备选），按 [人工确认](../../../workflow/execution-contract.md#人工确认) 获真实用户批准后更新为 `req_approved`。复杂需求的实施前独立审查与最终独立验收遵循 [实施与完成门槛](../../../workflow/execution-contract.md#实施与完成门槛)，由主会话统一协调派发。
