# 通用安装、恢复与升级

先读包规则和当前宿主适配。所有操作由宿主文件工具完成，摘要用实际计算工具取得；下列数据不是新调度程序。初始化不运行无关业务测试，不扫描历史证据，只处理包白名单和目标配置。

## GitHub/Git URL 获取

用户只提供仓库 URL 时，先在宿主临时目录获取仓库，再从**实际检出的同一提交**读取本 Skill 及包内规则。官方源码为 https://github.com/vvgool/multi-agent-requirement-workflow；其他明确 Git 来源同样按以下规则核验，不把 GitHub 设为唯一支持平台。

1. 先读取目标项目已有锁。已有 Git 锁必须使用锁中的 location 和完整 revision，忽略 URL 提示中的“最新版本”；提示来源不同时报告差异，不重绑。已有 manual 锁或旧快照按原兼容规则处理，不因 Git 来源可用就换源。无锁时采用用户明确 URL，revision 未指定则查询远程默认分支；指定分支/tag 时实际解析其提交。
2. 用现有 Git/连接能力获取代码到独立临时目录，不克隆进业务源码或覆盖现有目录。读取操作如 `git ls-remote --symref <url> HEAD` 可确定默认分支；拉取后用 `git rev-parse HEAD` 取得完整提交 SHA。命令参数须安全引用；私有仓库使用现有认证，不把凭据放进 URL、日志、锁或提示。没有 Git 获取能力或无权限时明确阻塞，不安装额外工具。
3. 从该提交干净检出的白名单内容计算包摘要，读取 framework.yaml，并核对锁中已有身份。确认实际 HEAD 等于最终锁定 revision；远程分支在获取期间变化时，以实际获取且核验的提交为准，报告该提交。使用归档或已有本地克隆时同样必须证明文件属于指定提交；修改后的工作树不能声称 Git 来源。
4. source.kind=git、location=实际无凭据仓库 URL、revision=实际完整提交 SHA；version 来自 framework.yaml，sha256 来自真实内容。branch、tag、latest 和网页 URL 不是 revision。锁建立后不在后续初始化重新解析分支。返回实际来源与 SHA，然后执行下述预检和安装；读取一个网页或下载单个 SKILL.md 不等于取得完整包。

获取失败或包校验失败时不写业务项目。只清理自己创建且未被修改的临时内容。临时 Git 获取属于初始化文件准备，不新增运行时 CLI；业务阶段仍由宿主原生角色执行。

## 预检

1. 定位目标真实根目录、当前宿主及包源。工作空间可位于其他目录；不读取整仓业务代码，仅加载适用规则与已有配置。逐层检查 AGENTS.md、CLAUDE.md（适用时）、workflow*.yaml、.gitignore、.agents、本机控制文件、缓存及当前宿主定义路径，拒绝坏链接、特殊文件和解析后逃出项目的链接。项目根自身可解析为真实路径，不据此依赖旧机器目录。
2. 校验 workflow.yaml；已有内容逐字段按配置规则验证，不能要求等于默认值。版本锁按包规则验证，未知字段/重复键拒绝。锁存在时必须取相同身份包；从提供源取得的内容先在宿主临时目录计算摘要。手动初次安装由用户提供的当前包计算真实身份与 manual 来源；Git 包须实际核实完整提交与摘要。下载/拉取失败保留项目原状，不安装额外工具或改凭据。
3. 检查旧快照/旧 pending，不能覆盖其角色、区块或历史。新回执存在时核对它的拥有项；源包或模板变化列差异，只有显式升级可继续。新回执不存在而锁已提交时视为新机器恢复：锁定包必须已核实，现有薄角色、入口和忽略区块须逐字节等于该包模板生成结果，才能认领本框架指定项；同名其他内容停止。无锁、无回执的残留不接管。同一项目已有 pending 时走下述恢复，不重新规划。
4. 检查当前宿主同名原生声明、禁用设置及入口遮蔽，遵循适配说明。新目标先要求不存在；已有无关角色/设置保持原字节。AGENTS、CLAUDE、.gitignore 仅计划追加标记区块；标记缺半、重复或用户编辑先停止。只生成当前宿主的三个角色；不生成一个协调子角色或另外两个宿主文件。

## 计划与写入

使用真实 [锁模板](../assets/templates/workflow.lock.yaml)、[项目入口](../assets/templates/project-entry-light.md)、[忽略区块](../assets/templates/gitignore.txt)，以及适配说明指定的原生模板和 [共用角色正文](../assets/templates/role-body.md)。以 logical role 的 product/development/testing 选择对应角色与阶段 Skill，所有占位符须替换。角色正文在各宿主原生定义中实际展开，不依赖额外启动脚本。

在任何目标写入前，独占创建 `.agents/requirement-workflow.pending.json`（可先建核验过的 .agents 容器）。schema_version=2，记录操作 install/restore/add_host/upgrade、host、锁定package/source、原锁实际摘要或absent、所有计划文件路径与before（absent或真实摘要）/after_sha256、区块原文件整字节与区块预期摘要、缓存逐文件清单、旧回执摘要和实际temporary_files。不得伪造恢复来源；计划不含凭据，路径均相对项目。保存并回读后才开始修改。

先保存 .gitignore 的拥有区块以忽略新本地内容。根工作空间不是 Git 仓库也写这个区块，便于之后共享。Git 仓库中缓存/本机回执/pending 已在索引时报告 local_state_tracked，不能只加忽略后声称不提交；不自动修改暂存区。再按清单准备包到 `.agents/requirement-workflow-cache/<sha256>`，逐文件核验且无额外文件才作为有效包。缓存不可指回源目录或其他项目，目录只读约定不改变业务文件权限。

所有写入先用同目录临时文件准备完整字节，临时路径先登记 pending；落位前重查目标仍为before，再原子替换并回读。新薄角色和所需入口区块完成后写锁（已有同锁保持原字节），不把初始化元数据塞入业务状态。保存或合并 `.agents/requirement-workflow.local.json`，拥有项只登记薄文件与区块、缓存清单；新增宿主保留其他宿主探测事实。核对包、拥有项、锁、配置及当前宿主三角色映射后才清理本次匹配的临时文件和 pending。回执不自包含自身摘要。

## 重复、中断和升级

- 相同锁/当前适配/缓存/拥有区块一致：不重写、不改时间，不重跑业务或冒记原生生效。仅缺缓存时按同锁补包；仅缺本机回执时按上文克隆恢复核对。当前宿主未激活仍返回 pending。
- 同一包新增宿主：核验已安装内容后只增加该宿主薄文件及必要桥接，复用入口、锁和缓存；已有宿主回执保持。新宿主不能继承旧宿主 passed。
- pending 恢复：先核对全部项目项再写；每项仅允许原before或计划after，缓存只允许计划中文件，计划外文件/摘要/链接变化停止。已为after的跳过，仍为before的按原包恢复；来源已改变或无法还原预期字节则 blocked。共同控制文件 pending/local 若已同时存在，先核对它们与计划/真实内容一致再清理；不能凭“有清单”就删 pending。AGENTS 等只接受计划中的原整文件或追加后整文件，不覆盖用户中途编辑。
- 明确升级：先证明旧任务全部结束，核对拥有文件未被用户修改；新包与协议可用后按同样计划更新缓存、薄角色/区块及版本锁，旧业务文稿、审批和run不动。保持旧缓存；无法可靠判定协议变化时停在原版本，不宣称自动迁移。当前版本不提供自动卸载或缓存回收。

## 结束检查

实际检查 YAML/TOML及Markdown前置元数据、所有包内本地链接、缓存摘要和角色路径、原项目内容保留、精确忽略区块、无包文件进入Git索引、无额外角色/Skill副本。回执按宿主契约记录；需提交清单只列实际产生/修改的配置、锁、入口、三个薄角色与忽略区块。宿主没有重新加载或原生角色选择能力时停止探测并解释缺项，不把安装判为全部生效。
