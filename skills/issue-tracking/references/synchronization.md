# 评论写入、去重与恢复

只由协调层在保存本地业务事实后执行。先读当前有效策略、绑定、授权、源事件与根状态版本；目标改变/授权撤销/策略停用时只保存原记录，不访问或转发。记录目录和文件须是当前需求内真实路径，拒绝来源不明内容、越界链接或已有不符摘要的记录。

## 准备记录

1. 从已存在的 events.jsonl 读取原 event_id、修订、业务 state_version、kind、摘要及证据，核对真实阶段交接。同步重试不能生成新业务事件或改原发生时间。没有事件但有状态时先按状态恢复规则核实并补事件，不凭当前 stage 猜历史成功。
2. sync_key 是 UTF-8 紧凑 JSON 数组 `[feature_id, revision, event_id, provider, host, repository, issue_number]` 的 SHA-256（ensure_ascii=false，无额外空格；revision/issue_number 为整数，其余为字符串）。数组取已核实的固定身份，摘要用实际工具算，不能编造。相同事件/目标永远取同一 key。
3. 读真实 [评论模板](../assets/templates/comment.md)，按原事件生成 comment.md，计算实际字节 body_sha256，先保存 pending record，再登记根 sync_records 和状态事件。事件/目标/正文一旦进入发送流程不可改写；修正事实在后续有依据的允许业务事件中显式说明，不覆盖历史；不另造未定义的留痕事件类型。原子落盘并回读，已有 key 先核对身份/摘要，不覆盖。

## 每次尝试

1. 核对记录正文摘要、原事件、授权目标及真实平台身份；写前再次确认 Issue 未被换绑。先查询已有评论并读取原始 body，按平台完成分页；只有完整可读且目标可靠时才能判断未发现。找到同 key 且正文摘要匹配时保存真实回执并回读核实，记 synced，不重复 POST；多个匹配或同 key 不同正文则 blocked，保留差异，不编辑/删除评论。
2. 只有 pending（未尝试或已明确确认未创建）且没有既存评论时，先将 record 改 sending、记录本次尝试与真实时间，回读确认后调用一次创建评论。正文使用保存的原字节，通过结构化工具参数或安全 body-file 传递，不经 shell 插值拼接。
3. 收到评论 ID 后保存回执，读取同一目标评论，核对标识及正文摘要，才记 synced。若无法读取、返回不完整、写入超时、连接中断或 sending 时中断，记 unknown，保留能取得的 ID/响应事实；不能把“请求已发出”当成功。
4. 权限不足、身份/正文冲突、缺能力记 blocked；明确的未创建临时失败保留 pending 并说明解除条件。传输错误无法确定服务端是否执行时属于 unknown。每个事件每次协调轮次至多一次创建请求，禁止循环重试或后台轮询；业务流程照常推进。

## 恢复

- synced：保留真实回执，不重新发；发现回执与正文/目标冲突时只记录异常，不静默重建被删除/修改的评论。
- sending/unknown：有评论 ID 时优先直接读该评论，否则完整分页查询同 key。唯一匹配并核实正文后补记 synced。没有找到不能单凭列表为空就断言未创建；缺分页、可见性或服务端最终结果证据时保持 unknown，不重发。只有能证明原请求未执行/平台明确未创建，才回 pending；长期无法确认时交用户决策，不自动承担重复写入风险。
- blocked/pending：解除对应条件后按同一 key 和原正文重新核对，再决定是否创建。不能用新的 run_id 或时间逃过去重。

更新 record、根 sync_status/索引和 issue_sync_* 事件采用单协调会话与 state_version 检查。写后本地中断时先读回 record、回执和实际远端事实再补齐；不清理记录或原 comment.md。所有“已同步”均须有可复核的读取事实。无持久幂等键的平台不能保证严格只写一次，未知写入宁可保留待核实。
